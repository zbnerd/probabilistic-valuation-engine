# 1장: 첫 번째 측정 — 현재가 얼마나 느린가

> "측정 없는 최적화는 미신이다." — 5-Agent Council

## 문제: 정확한 성능을 모른다

2026년 1월 20일, 5-Agent Council이 첫 번째 부하 테스트를 실시했다. 도구는 Locust, 대상은 Nightmare Chaos 시나리오. 750명 동시 사용자, 5분간 요청을 쏟아부었다.

## 결과: 223 RPS

```
╔════════════════════════════════════════════════════════════╗
║  Total Requests:  67,148                                   ║
║  RPS (avg):       223 req/sec                              ║
║  Success Rate:    40.30% (27,063 successful)                ║
║  Failure Rate:    59.70% (40,085 failures — mostly 429)     ║
║  p50 Latency:     1,800ms                                  ║
║  p99 Latency:     4,100ms                                  ║
║  Max Latency:     9,608ms                                  ║
╚════════════════════════════════════════════════════════════╝
```

59.7% 실패율. 하지만 이건 **의도된 것**이었다. 대부분이 429 Rate Limited 응답으로, Rate Limiter가 시스템을 보호하고 있었다. 실제 문제는 다른 곳에 있었다.

## 발견한 병목들

### 1. Redis 네트워크 왕복 지연

캐시 조회마다 Redis를 거쳐야 했다. 로컬 Docker 환경이어도 매 요청마다 1~2ms가 추가되었다. 223 RPS × 3~5회 Redis 호출 = 초당 1,000회 네트워크 왕복.

### 2. 동기 DB 저장

계산 결과를 MySQL에 저장하는 데 15~30ms. 캐시 미스 시 이 시간이 고스란히 응답 시간에 추가되었다.

### 3. Executor 스레드풀 대기

`expectationComputeExecutor`: core 4, max 8, queue 200. 223 RPS 중 절반은 Rate Limit에 걸린 것이고, 실제 계산 요청만으로도 스레드풀이 포화 상태였다.

### 4. N+1 쿼리

`GameCharacterRepository`에서 `LEFT JOIN FETCH` 없이 연관 엔티티를 조회하는 곳이 있었다. 쿼리 하나가 10개의 추가 쿼리를 낳았다.

## 무엇을 고민했나

Council은 두 가지 접근을 논의했다:

**A안: 인프라 확장** — Redis 클러스터 구성, MySQL 읽기 복제본 추가, 인스턴스 스케일업
**B안: 애플리케이션 최적화** — 캐시 전략 개선, 비동기 처리, 쿼리 최적화

비용을 고려했다. AWS t3.small 월 $15. A안은 최소 $100 이상으로 올라간다. B안으로 가기로 했다.

## 다음 단계

첫 번째 타겟은 **Cache Stampede**였다. 캐시가 만료되거나 존재하지 않을 때, 동일한 키에 대한 요청이 동시에 몰리면 모두가 독립적으로 계산을 수행한다. 100명이 같은 캐릭터를 요청하면 100번의 Nexon API 호출이 발생한다.

이를 막기 위해 **Singleflight 패턴**을 도입하기로 했다. 동일한 키에 대한 요청을 하나로 합쳐서, Leader 1명만 계산하고 나머지는 결과를 공유받는 방식이다.
