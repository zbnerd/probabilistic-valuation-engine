# 6장: 정합성의 대가 — 속도를 희생하다

> "올바른 데이터를 느리게 주는 것과, 빠르게 틀린 데이터를 주는 것. 어느 쪽인가?"

## 문제: Scale-out이 안 된다

965 RPS를 달성했지만, 단일 인스턴스의 한계에 부딪혔다. 서버를 늘려도 **데이터가 불일치**한다.

인스턴스 A에서 캐릭터 "아델"의 기대비용을 새로 계산해 L1 캐시에 저장했다. 하지만 인스턴스 B의 L1 캐시에는 여전히 이전 값이 남아 있다.

```
Instance A: 아델 totalExpectedCost = 343,523,928,885,098 ← 최신
Instance B: 아델 totalExpectedCost = 342,100,000,000,000 ← 구버전
Instance C: 아델 totalExpectedCost = 343,523,928,885,098 ← 최신 (우연히)
```

사용자가 새로고침할 때마다 다른 결과가 보인다. **데이터 정합성**이 깨진다.

## 고민: 세 가지 선택지

```
┌─────────────────────────────────────────────────────────────────┐
│  Option A: Redis 공유 캐시                                      │
│  모든 인스턴스가 Redis에서 읽는다.                               │
│  → Redis가 SPOF (Single Point of Failure)                      │
│  → 네트워크 지연 +1~2ms 매 요청마다                              │
│  → Redis 클러스터 구성 비용                                      │
│                                                                 │
│  Option B: 캐시 포기                                            │
│  매 요청마다 DB 조회                                             │
│  → DB 부하 급증                                                 │
│  → Latency 100ms+ 증가                                         │
│                                                                 │
│  Option C: 인메모리 유지 + Pub/Sub 동기화                        │
│  각 인스턴스 독립 L1 + 변경 시 Redis Pub/Sub로 무효화 전파       │
│  → 최종 일관성 (eventual consistency)                           │
│  → Redis Pub/Sub은 트랜잭션 보장 없음                            │
│  → 메시지 유실 가능                                             │
└─────────────────────────────────────────────────────────────────┘
```

**V5 Stateless** 아키텍처를 선택했다. Write-Behind Buffer를 인메모리에서 Redis로 옮기고, Redis Pub/Sub으로 캐시 무효화를 전파한다.

## 구현: V5 Stateless

```
V4 (In-Memory Buffer):          V5 (Redis Buffer):
┌─────────────┐                 ┌─────────────┐
│  Instance A │                 │  Instance A │
│  [Buffer]   │                 │     │       │
└─────────────┘                 │     ▼       │
┌─────────────┐                 │  ┌─────┐    │
│  Instance B │                 │  │Redis│◄───┼─── 모든 인스턴스가
│  [Buffer]   │                 │  │Buffer│   │    공유 버퍼 사용
└─────────────┘                 │  └─────┘    │
  ⚠️ Data Inconsistency          └─────────────┘
                                  ✅ 100% Consistency
```

### 데이터 정합성 검증

```
캐릭터: 아델
Instance 1-5: {"totalExpectedCost":343523928885098,"fromCache":true}
MD5 Hash: a3a29fd2f4f5eede4171712a5c8920a1
→ 모든 인스턴스에서 동일한 해시값. 정합성 확보!
```

## 결과: 325 RPS (−53% 성능 저하)

2026년 1월 27일:

```
╔════════════════════════════════════════════════════════════╗
║  V5 STATELESS                                              ║
║  단일 인스턴스:                                             ║
║  - V4 Single:  688 RPS                                     ║
║  - V5 Single:  325 RPS (−53%)                              ║
║  4-인스턴스:                                               ║
║  - V5 4-Instance: 510 RPS (WSL2 리소스 경합)               ║
║    ※ 이후 Auto Warmup 도입으로 940 RPS로 개선 (7장 참조)     ║
╚════════════════════════════════════════════════════════════╝
```

**정합성은 확보했지만 속도가 절반으로 줄었다.**

### 원인

1. **Redis 네트워크 비용**: 매 write마다 Redis를 거쳐야 한다. 로컬 메모리 0.1ms → Redis 2~5ms
2. **Pub/Sub 오버헤드**: 캐시 무효화 이벤트를 Redis에 발행하는 비용
3. **WSL2 리소스 경합**: 4개 인스턴스를 로컬에서 돌리니 CPU/메모리 경합

### 트레이드오프 분석

| 요소 | V4 (In-Memory) | V5 (Redis) |
|------|----------------|------------|
| 단일 인스턴스 RPS | 688 (100%) | 325 (47%) |
| Scale-out | ⚠️ 불일치 | ✅ 선형 확장 |
| Rolling Update 안전 | ⚠️ 데이터 유실 | ✅ 안전 |
| RPS/$ (단일) | 45.9 | 21.7 |

## 결정: V5는 Scale-out 시에만 사용

```
Decision:
- 단일 인스턴스: V4 (688 RPS, 데이터 정합성 약간 희생)
- Scale-out 필요 시: V5 (325 RPS, 완전한 정합성)
- V5는 "보험"이다. 당장 필요 없으면 V4를 쓴다.
```

이 결정은 나중에 **PostgreSQL NOTIFY**가 등장하면서 완전히 뒤바뀐다. 8장에서 다시 이야기하자.

## 새로운 문제: 콜드 스타트

V5의 325 RPS도 사실 **캐시가 따뜻해진 상태**의 수치였다. 처음 시작할 때, 아무 캐시도 없는 상태에서는 얼마나 느릴까?

테스트해보니 **287 RPS**. 타임아웃 20%+. p50 760ms.

서버 재시작 후 첫 요청들이 가장 느리다. 이 문제를 해결하려면 **미리 캐시를 채워야** 한다.
