# 11장: 에필로그 — 97에서 7,347, 그리고 그 너머

> "숫자가 아니라 의사결정의 기록이다."

## 여정의 한 줄 요약

```
2026년 1월 20일:  97 RPS — "서버가 느리다"
2026년 3월 30일: 7,347 RPS — 수십만 실데이터, 캐시 정합성 보장, Scale-out 준비 완료
```

**76배 향상.** 113배가 아니다. 10,994는 빈 데이터베이스에서의 이상적 수치였다. 현실에서는 수십만 건의 데이터, 캐시 미스, DB 쓰기 경합이 모두 포함된 **7,347 RPS**가 진짜 성과다.

그리고 이 7,347 RPS는 **분산 환경을 고려한 수치**다. 캐시 정합성이 보장되고, 노드 추가만으로 선형 확장이 가능하다.

## 각 장의 교훈

### 1장 — 측정 없는 최적화는 미신이다

첫 부하 테스트에서 223 RPS를 측정했다. 추측이 아니라 측정. 이 숫자가 없었으면 어디서부터 시작해야 할지 몰랐을 것이다.

### 2장 — 이론상 완벽한 최적화가 최악의 결과를 낳을 수 있다

LocalSingleFlight는 이론적으로 완벽했다. 하지만 캐시 히트마저 blocking하면서 56% 성능 하락을 초래했다. **"잘못된 곳에 적용된 최적화는 최악의 병목이다."**

### 3장 — 가장 큰 성과는 발상의 전환에서 온다

L1 Fast Path는 새로운 알고리즘이 아니었다. "이미 GZIP으로 압축된 걸 왜 풀었다가 다시 압축하지?"라는 질문에서 시작했다. 473% 성능 향상은 코드 추가가 아니라 **코드 제거**에서 나왔다.

### 4장 — 비동기는 만병통치약이 아니다

Write-Behind Buffer는 DB 저장을 150ms에서 0.1ms로 줄였다. 하지만 Phaser 기반 shutdown safety, CAS 기반 동시성 제어, Backpressure 처리가 필요했다. 비동기는 복잡도를 앞으로 미루는 것이지, 없애는 것이 아니다.

### 5장 — 병렬화에는 항상 함정이 있다

3개 프리셋 병렬 계산. 간단해 보였지만 같은 Executor에서 부모-자식을 실행하면 데드락이 발생한다. 해결은 전용 Executor 분리. **"병렬화는 스레드를 나누는 것이 아니라, 문제를 나누는 것이다."**

### 6장 — 정합성과 속도는 트레이드오프다

V5 Stateless는 정합성을 확보했지만 RPS가 절반으로 줄었다. Scale-out을 위해서는 이 대가가 필요했다. **"모든 것을 가질 수는 없다. 무엇을 포기할지 선택해야 한다."**

### 7장 — 차가운 시작은 모든 시스템의 약점이다

Cold Start에서 20% 타임아웃. 해결은 Auto Warmup. 전날 인기 캐릭터 100개를 미리 캐시에 채우는 것만으로 227% 향상. **"준비된 시스템은 준비되지 않은 시스템보다 항상 빠르다."**

### 8장 — 더 적은 기술로 더 많은 것을

Redis, MySQL, MongoDB를 버리고 PostgreSQL 하나로 통합. 이 결정이 없었으면 PostgreSQL NOTIFY도, 단일 인프라 운영도 불가능했다. **"복잡도를 줄이는 것이 성능을 높이는 가장 확실한 방법이다."**

### 9장 — 가까이에 답이 있을 수 있다

PostgreSQL NOTIFY는 새로운 기술이 아니다. PostgreSQL 9.0(2010년)부터 있었다. 하지만 Redis에 익숙해져서 보지 못했다. **"도구를 바꾸기 전에, 이미 가진 도구를 다 썼는지 확인하라."**

### 10장 — 현실은 항상 벤치마크보다 느리다

빈 DB에서 10,994 RPS. 200k~300k rows에서 7,347 RPS. 33% 하락. 하지만 이 7,347이 믿을 수 있는 수치다. **"낙관적인 측정에 기반한 계획은 항상 실패한다. 보수적인 측정에 기반한 계획은 성공한다."**


## 76배 향상의 비밀 — 네 가지 원인

```
1. 인프라 복잡도 제거 (8장)
   Redis + MySQL + MongoDB → PostgreSQL 하나
   → 네트워크 홉 감소, 운영 단순화, 장애 포인트 축소

2. Zero-Copy 캐시 경로 (3장)
   매 요청 300KB 직렬화/역직렬화 → GZIP byte[] 그대로 반환
   → 캐시 히트 응답 200ms → 4ms

3. 비동기 쓰기 + 병렬 계산 (4~5장)
   동기 DB 저장 150ms → Buffer.offer 0.1ms
   순차 계산 300ms → 병렬 계산 100ms

4. 원자적 캐시 무효화 (9장)
   Redis Pub/Sub (eventual) → PostgreSQL NOTIFY (transactional)
   → Scale-out 시 캐시 정합성 보장 → 선형 확장 가능
```

## 마지막 교훈

이 여정에서 가장 중요한 것은 숫자가 아니었다. 숫자는 결과일 뿐이다.

중요한 것은 **의사결정의 과정**이었다.

1. **측정하고, 추측하지 마라.** 97 RPS에서 시작해 매 단계마다 측정했다. 측정 없는 최적화는 미신이다.

2. **단순함이 성능이다.** Redis, MySQL, MongoDB를 버렸을 때 성능이 아니라 복잡도가 줄었다. 그런데 성능도 올랐다. 복잡도가 성능의 적이다.

3. **트레이드오프를 명시하라.** V5 Stateless는 속도를 포기하고 정합성을 얻었다. 이 포기를 명시적으로 결정하지 않았으면, 계속 "왜 느리지?"만 반복했을 것이다.

4. **현실에서 측정하라.** 빈 DB의 10,994 RPS는 자랑거리가 아니다. 200k~300k rows의 7,347 RPS가 진짜다. 낙관적인 수치에 기반한 계획은 항상 실패한다.

5. **오버엔지니어링을 의심하라.** 5-20 QPS에 분산 버퍼 + 메시지 큐를 구축하는 것은 "나중을 위한 준비"가 아니다. "나중"이 오면 그때 구축하면 된다. 문제를 이미 알고 있으니까.
