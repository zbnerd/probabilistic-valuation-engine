# 분산된 DB·캐시·메시징 구조로 인해 발생한 복잡도와 비용을 절감하기 위한 PostgreSQL 아키텍처 통합 프로젝트

```jsx
분산 DB/캐시/메시징 구조에서 발생한 커넥션 병목과 운영 복잡도를
PostgreSQL 기반 단일 트랜잭션 구조로 재설계하여 해결한 프로젝트
```

## 1. 분산된 DB·캐시·메시징 구조에서 발생한 커넥션 분산 및 운영 복잡도 문제 발생 및 PostgreSQL 단일화로 DB 3개 → 1개 및 Redis 제거하여 비용 절감 및 시스템 단순화

**RDS 2→1 축소, 캐시/큐 인프라 제거를 통해 비용 절감 및 운영 복잡도 감소**

2. **DB별 커넥션 풀 분산 + Scheduler Polling으로 커넥션 리소스 낭비 및 Alert 발생**

<aside>
💡

**커넥션 풀 부족으로 보였던 성능 저하 문제를 부하 테스트와 메트릭 분석을 통해 구조적 병목으로 재정의**

**멀티 DB 환경과 polling 기반 구조로 인해 커넥션이 비효율적으로 점유되는 문제를 식별**

**단순 튜닝이 아닌 아키텍처 재설계가 필요한 문제임을 도출**

</aside>

### **문제 (Problem)**

초기에는 단순히 커넥션 풀 사이즈 문제로 보였다.

하지만 실제 부하 테스트와 모니터링을 통해, 이 문제는 단순 튜닝으로 해결할 수 없는 **구조적 병목**임을 확인했다.

- Thread 200 vs Connection 25 (12.5%) 불균형
- 다수 요청이 커넥션을 획득하지 못하고 대기 상태
- 요청 처리 시간의 대부분이 실제 로직이 아닌 커넥션 대기 시간에 소비
- 일부 구간에서 커넥션 풀 고갈 (Pool Exhaustion) 발생
- 사용자 관점에서 응답 지연 및 타임아웃 발생
- Redis / MySQL / MongoDB 각각 별도 커넥션 풀
- 하나의 요청이 여러 DB 커넥션을 동시에 점유
- Scheduler 기반 polling 구조 → 일부 커넥션이 장시간 점

### **선택지 (Options)**

- **A. 커넥션 풀 사이즈 증가**
    - 장점: 빠른대응 가능
    - 단점: 근본 문제 해결 불가(대기구조 유지)
- **B. DB별 커넥션 튜닝 및 분산 최적화**
    - 장점: 일부 개선 가능
    - 단점: 복잡도 유지 + 문제 재발 가능성
- **C. 구조적 문제 재정의 및 아키텍처 개선**
    - 장점: 병목 근본 해결 가능
    - 단점: 설계 변경 필

### **결정 (Decision)**

**C. 구조적 문제로 판단하고 아키텍처 레벨에서 해결하기로 결정**

단순 커넥션 수 증가가 아니라

- 요청 처리 구조
- 커넥션 사용 방식
- 데이터 흐름 구조

전체를 재검토해야 하는 문제로 정의 

### **구현 (Implementation)**

이 단계에서는 직접적인 해결보다 문제의 본질을 드러내는데 집중했다.

- HikariCP / Thread Pool 메트릭 분석
- 요청 처리 흐름 추적 (Thread → DB → 응답)
- 커넥션 사용 패턴 분석

커넥션 부족이 아니라 커넥션이 낭비되는 구조임을 식별.

### **결과 (Result)**

- 커넥션 병목의 **근본 원인이 구조 문제임을 명확히 정의**
- 이후 Polling, 멀티 DB, 메시징 구조 문제로 분석 확장
- 단순 튜닝이 아닌 **아키텍처 재설계 필요성 도출**

## **3. Outbox 기반 메시징 처리에서 10~15초 주기 Scheduler Polling으로 상시 커넥션 점유 문제 발생하여 이벤트 기반 처리(PGMQ)로 전환하고 불필요한 DB 접근 및 커넥션 점유 제거**

"어디에서 커넥션이 낭비되고 있는가"를 추적하기 시작했다.

### **문제 (Problem)**

커넥션 병목을 구조적 문제로 재정의한 이후, 단순 커넥션 부족이 아니라 **커넥션 사용 방식 자체를 분석**하기 시작했다.

특히 Outbox 기반 구조에서 여러 Scheduler가 독립적으로 polling하며 상시 커넥션을 점유하는 구조가 형성되어 있었다.

다이어그램에서 보이듯이, 여러 Scheduler가 각각 DB에 polling을 수행하면서 동시에 다수의 커넥션을 점유하는 구조였다.

분석 과정에서, Scheduler 기반 polling 구조가 지속적으로 DB 커넥션을 점유하고 있음을 확인했다.

- Outbox 테이블 기반 메시징 처리
- Scheduler가 주기적으로 DB를 polling
- 이벤트 발생 여부와 관계없이 지속적인 DB 조회 발생

즉, 문제는 커넥션 수가 아니라 **요청 처리 방식 자체(polling 구조)**였다

- Scheduler가 일정 주기로 DB를 반복 조회
- 이벤트가 없어도 불필요한 쿼리 지속 발생
- 커넥션이 장시간 점유되어 가용 커넥션 감소
- 실제 트래픽과 무관하게 DB 부하 발생

특히 Outbox 기반 구조에서 여러 Scheduler가 독립적으로 polling하며 **상시 커넥션을 점유하는 구조**가 형성되어 있었다

### 1) Polling 기반 메시징 구조

기존 구조:

- Outbox 테이블
- Scheduler (10s ~ 15s 간격 polling)
- Redis Stream 연계 처리

👉 이벤트 발생 여부와 무관하게 DB 조회 발생

### 2) 커넥션의 “숨은 소비자”

- OutboxScheduler
- EventOutboxScheduler
- 외부 API 연계 Scheduler

👉 각각 별도의 커넥션을 점유

실제 분석 결과,

Scheduler만으로도 다수 커넥션이 상시 점유되고 있었으며

이는 비즈니스 요청이 사용할 수 있는 커넥션을 감소시키는 원인이었다

### 3) 구조적 한계

Polling 구조는 다음과 같은 한계를 가짐:

- 이벤트 없음 → 불필요한 DB 조회 발생
- 이벤트 많음 → polling 주기 한계로 처리 지연
- 커넥션 사용이 “요청 기반”이 아니라 “시간 기반”

👉 즉, **리소스 사용이 비효율적으로 고정됨**

### **선택지 (Options)**

- **A. Polling 주기 조정**
    - 장점: 간단한 개선
    - 단점: 근본 문제 해결 불가
- **B. 이벤트 기반 메시징 구조로 전환**
    - 장점: 불필요한 DB 조회 제거
    - 단점: 구조 변경 필요
- **C. Scheduler 수 및 쿼리 최적화**
    - 장점: 일부 부하 감소
    - 단점: 구조 유지, 커넥션 점유 지속

### **결정 (Decision)**

**B. Polling 구조를 이벤트 기반 처리로 전환하기로 결정**

문제를 단순 커넥션 사용량이 아니라

- 메시징 처리 방식
- 이벤트 흐름 구조
- 리소스 사용 패턴

의 문제로 정의하고,

**Polling → Event-driven 구조 전환**이 필요하다고 판단했다.

### **구현 (Implementation)**

Polling 기반 Outbox 구조를 제거하고,

**PostgreSQL 기반 메시징(PGMQ) 구조로 전환**

→ 여러 Scheduler가 개별적으로 DB를 조회하던 구조를 단일 Queue 기반 이벤트 처리 구조로 통합

### 핵심 변경

- Outbox + Scheduler polling 제거
- Redis Stream 제거
- PostgreSQL 기반 메시지 큐(PGMQ) 도입

### 효과

- 이벤트 발생 시에만 처리 (Polling 제거)
- 메시징과 데이터 처리를 동일 DB 트랜잭션으로 통합
- Scheduler 기반 커넥션 점유 제거

### **결과 (Result)**

- Polling 제거로 **상시 커넥션 점유 문제 해소**
- 이벤트 기반 처리로 DB 불필요 접근 제거
- 메시징 구조 단순화 및 안정성 향상

→ 이 문제는 단순 메시징 방식의 문제가 아니라,데이터 저장, 캐싱, 메시징이 분산된 구조에서 발생한 문제임을 확인. 멀티 DB 구조 자체를 통합해야 한다는 결론으로 확장

### **문제 (Problem)**

Polling 제거 과정에서, 시스템 전반의 비효율이 특정 기능이 아니라 구조에서 비롯된 문제임을 발견

- Redis + MySQL + MongoDB로 분산된 구조
- 시스템 간 역할이 분리되어 있음
- 커넥션 분산 → 리소스 비효율
- 데이터 흐름 분리 → 처리 단계 증가
- 장애 포인트 증가 → 장애 전파

👉 **데이터, 캐시, 메시징의 책임이 서로 다른 시스템에 분산되어 있었음**

### **선택지 (Options)**

- **A. DB 중심으로 구조 통합 (PostgreSQL)**
    - 데이터 + 이벤트 + 메시징 통합
    - 단일 트랜잭션 기반 처리

👉 **구조 자체를 단순화**

- **B. 기존 구조 유지 + 튜닝**
    - 커넥션 풀 조정
    - Scheduler 최적화
    - Redis 성능 개선

👉 **문제는 완화되지만 구조는 그대로 유지됨**

- **C. 메시징 구조만 개선**
    - Kafka / Redis Stream 고도화
    - Outbox 패턴 유지

👉 **이벤트 처리 개선 가능하지만 데이터-메시징 분리는 그대로**

### **결정 (Decision)**

**A. DB 중심 통합 구조 채택** 

**선택 이유**

- 문제의 본질이 “성능”이 아니라 “구조 분산”에 있었음
- 분산된 책임을 하나의 시스템으로 통합 필요
- 트랜잭션 단위에서 데이터와 이벤트를 함께 처리하기 위함

### **구현 (Implementation)**

### 1) 데이터 통합

- MySQL + MongoDB → PostgreSQL 통합
- JSONB 활용하여 비정형 데이터 처리

### 2) 메시징 구조 변경

- Outbox + Scheduler 제거
- PGMQ 기반 메시징 도입

### 3) 이벤트 처리 방식 변경

- Polling → NOTIFY / LISTEN 기반 이벤트 처리

### 4) 캐시 전략 변경

- Redis 제거
- 애플리케이션 L1 캐시 + DB 기반 이벤트로 동기화

### **결과 (Result)**

### 1) 제거된 요소

- Redis
- MongoDB
- Outbox
- Scheduler
- Polling 구조

### 2) 개선 효과

- 단일 DB → 커넥션 효율 개선
- 트랜잭션 통합 → 데이터 정합성 확보
- 구조 단순화 → 운영 난이도 감소
- 장애 범위 축소 → 안정성 향상

### 3) 비즈니스 임팩트

- 인프라 비용 감소
- 장애 대응 속도 개선
- 시스템 이해도 향상

## **5. 외부 API 연동 구조에서 장애 발생 시 Thread Pool 고갈로 전체 서비스 다운 문제 발생 및 의존성 격리(Bulkhead) 구조 도입으로 장애 전파 차단 및 서비스 가용성 향상**

<aside>
💡

외부 API 장애가 발생할 경우 Thread Pool 고갈로 인해 서비스 전체가 중단되는 문제가 있었음

원인은 외부 의존성에 대한 격리 구조가 없어 장애가 시스템 전체로 전파되는 구조

의존성 격리(Bulkhead) 기반으로 구조를 개선하여 장애 전파를 차단하고 서비스 가용성을 확보

</aside>

### **문제 (Problem)**

**외부 API 장애가 시스템 전체로 전파되며 서비스 전체 장애로 확장**

### 1) 현상

- 외부 API 응답 지연 / 실패
- Thread pool 점유 증가
- 전체 요청 처리 불가

### 2) 결과

👉 **서비스 전체 다운**

### 3) 핵심 원인

**외부 의존성에 대한 격리 구조가 없었음**

### **선택지 (Options)**

- **A. 캐시 활용**
    - API 응답 캐싱

👉 **부하 감소는 가능하지만 장애 전파는 여전히 존재**

- **B. 의존성 격리 구조 도입 (Bulkhead / Isolation)**
    - 외부 API 전용 자원 분리
    - 실패 영향 범위 제한

👉 **장애 전파 차단**

- **C. 타임아웃 / 재시도 튜닝**
    - API timeout 조정
    - retry 정책 추가

👉 **일시적 완화 가능하지만 근본 해결 아님**

### **결정 (Decision)**

**B. 의존성 격리 구조 도입**

**선택 이유**

- 문제의 본질이 “응답 속도”가 아니라 “장애 전파”였음
- 일부 기능 장애가 전체 시스템 장애로 확장되는 구조 제거 필요
- 시스템 안정성 확보를 위해 격리 필수

### **구현 (Implementation)**

### 1) Thread Pool 분리

- 외부 API 호출 전용 thread pool 구성
- 내부 로직과 자원 분리

### 2) Timeout / Fail-Fast 적용

- 일정 시간 초과 시 즉시 실패 처리
- 대기 시간 최소화

### 3) Circuit Breaker

- 반복 실패 시 호출 차단
- 빠른 실패 유도

### 4) Fallback 처리

- 기본값 또는 대체 로직 적용
- 사용자 영향 최소화

### **결과 (Result)**

### 1) 개선 효과

- Thread pool 고갈 방지
- 장애 전파 차단
- 일부 기능 장애 시에도 전체 서비스 정상 동작

### 2) 비즈니스 임팩트

- 서비스 가용성 향상
- 장애 대응 부담 감소
- 사용자 신뢰도 개선
