# 프롤로그: 세 개의 데이터베이스와 97개의 요청

> 2026년 1월 20일, 화요일.

---

## 세 개의 심장

probabilistic-valuation-engine은 세 개의 심장으로 돌아가고 있었다.

**MySQL** — 사용자의 계정, 캐릭터 데이터, 좋아요 기록. 시스템의 진짜 심장.

**Redis** — 캐시, 분산 락, 메시지 큐(Streams), 세션 데이터. 빠르지만 휘발성인 두 번째 심장.

**MongoDB** — 이벤트 로그, 감사 기록. 영원히 남아야 하는 것들을 담은 세 번째 심장.

세 개의 데이터베이스는 각각 자신의 커넥션 풀을 가지고 있었다. HikariCP는 MySQL에 25개, Lettuce는 Redis에 50개, MongoDB 드라이버는 14개. 총 89개 이상의 커넥션이 늘 데이터베이스를 붙잡고 있었다.

그리고 **Nexon API** — 외부 서비스. 우리가 제어할 수 없는 유일한 심장.

---

## 97개의 요청

그날 부하 테스트 결과는 충격적이었다.

```
Throughput: 97 RPS
p99 Latency: 4,100ms
Error Rate: 59.7%
```

초당 97개. 10명의 동시 사용자도 제대로 처리하지 못하는 수준이었다. 60%에 가까운 에러율은 "서비스"라고 부르기 민망한 상태였다.

원인은 명확했다. 캐시가 없었다. 아니, 정확히는 캐시가 있었지만 제대로 작동하지 않았다. 모든 요청이 DB까지 내려가고, DB는 커넥션 풀 고갈로 요청을 거부하고, 거부된 요청은 타임아웃되고, 타임아웃은 에러로 기록되었다.

순환의 늪이었다.

## "장애가 뭔지도 몰랐던 시절"

당시의 코드베이스를 열어보면 장애에 대한 대비가 거의 없었다.

**try-catch 남용.** 모든 서비스 메서드가 자신만의 try-catch로 둘러싸여 있었다. 에러는 잡히지만 아무 로그도 남지 않았고, 호출자는 실패를 알 수 없었다. 실패를 삼키는 블랙홀이었다.

**서킷 브레이커 부재.** Nexon API가 응답하지 않으면? 스레드가 대기한다. 대기하는 스레드가 쌓이면? 스레드 풀이 고갈된다. 스레드 풀이 고갈되면? 다른 모든 요청도 처리하지 못한다. 외부 서비스 하나가 전체 시스템을 마비시키는 구조였다.

**분산 락의 무지.** Redis 분산 락은 있었지만, 락 키 생성 로직이 제각각이었다. 캐시 키와 락 키와 NOTIFY 페이로드가 서로 달랐다. 락이 해제되어도 아무도 알지 못했다.

**모니터링의 부재.** 커넥션 풀 사용률, 스레드 풀 상태, 외부 API 응답 시간 — 아무것도 모니터링하지 않았다. 장애가 발생해도 운영자는 사용자 불만을 통해서야 알 수 있었다.

## 첫 번째 장애대응 테스트

2026년 1월 20일, 우리는 시스템에 고의로 장애를 주입해보기로 했다.

"과연 이 시스템이 어디까지 버틸 수 있을까?"

장애대응 테스트 첫 번째 시나리오 — **MySQL Death**.

```sql
DROP TABLE character_like;
```

결과:

```
MySQL Crash: 시뮬레이션 완료
Circuit Breaker: TRIPPED within 2.5s ✅
Fallback Success: 18/30 (72%) ✅
Retry Attempts: 45 (Exponential Backoff + Jitter)
```

놀랍게도 서킷 브레이커는 작동했다. 기본적인 Resilience4j 설정이 있었던 것이다. 하지만 그게 전부였다. 더 복잡한 시나리오에서는 속수무책이었다.

장애대응 테스트 베이스라인: **223 RPS**.

97 RPS보다는 나았지만, 여전히 낮았다. 그리고 이것은 "잘 된" 케이스였다.

## 세 명의 관찰자

장애대응 테스트를 진행하면서 세 명의 관찰자가 시스템을 들여다보았다.

**Blue (Architect)** — 구조를 본다. "이 설계가 장애에 어떻게 반응하는가?"

**Red (SRE)** — 장애를 주입한다. "이 시스템이 어디서 부서지는가?"

**Purple (Auditor)** — 데이터를 검증한다. "장애 후에도 데이터가 온전한가?"

세 명의 시선이 모여야 비로소 전체 그림이 보였다. 나중에 이것은 5명의 **Agent Council**로 발전하지만, 그때는 세 명이면 충분했다.

## 이 책이 시작되는 곳

2026년 1월 20일. 97 RPS. 59.7% 에러율. 세 개의 데이터베이스. 장애에 무방비 상태인 시스템.

이것이 시작점이었다.

이 책은 여기서부터 시작해, 매번 장애를 겪고, 그 장애를 분석하고, 대응책을 세우고, 다시 장애를 주입해 검증하는 과정을 기록한다.

각 장은 하나의 장애 사건을 다룬다. 발생 → 탐지 → 분석 → 대응 → 검증. 이 5단계가 반복되면서 시스템은 조금씩 단단해졌다.

그리고 3개월 뒤, 7,347 RPS에 도달했다.

여정을 시작한다.
