# 1장: 도미노 — 외부 API 하나가 쓰러뜨린 전체 시스템

> "한 장의 도미노가 쓰러지면 나머지도 따라 쓰러진다. 우리 시스템은 도미노 그 자체였다."
>
> — 장애 회고, 2026년 1월

---

## 발생

Nexon API는 메이플스토리 캐릭터 정보를 제공하는 외부 서비스다. 우리 시스템은 사용자의 검색 요청이 들어오면 Nexon API를 호출해 캐릭터 데이터를 가져온다. 간단한 흐름이다.

그날 Nexon API가 응답을 멈췄다.

원인은 알 수 없었다. 그들의 서버 점검일 수도 있고, 네트워크 장애일 수도 있고, 아니면 그냥 느려진 것일 수도 있다. 중요한 건 원인이 아니었다. **우리 시스템이 어떻게 반응했는지**가 문제였다.

---

## 탐지

처음에는 느려졌다. 응답 시간이 50ms에서 500ms로, 500ms에서 2초로, 2초에서 5초로. 그리고 타임아웃.

하지만 아무도 몰랐다. 모니터링이 없었으니까.

사용자가 불만을 제기하기 시작했을 때야 장애를 인지했다. "사이트가 안 돼요." "계속 로딩만 돼요." 그제야 로그를 열어보았다.

```
java.util.concurrent.TimeoutException: null
    at java.base/java.util.concurrent.CompletableFuture.timedGet()
    at maple.expectation.infrastructure.external.impl.NexonDataCollector.fetchAndPublish()
    ... 67 more
```

TimeoutException. Nexon API 호출이 타임아웃되고 있었다. 하지만 이건 빙산의 일각이었다.

---

## 분석: 연쇄 붕괴의 메커니즘

로그를 더 파고들자 끔찍한 연쇄 반응이 보였다.

```text
[Thread-1] NexonDataCollector: 타임아웃 — 스레드 대기 중
[Thread-2] NexonDataCollector: 타임아웃 — 스레드 대기 중
[Thread-3] NexonDataCollector: 타임아웃 — 스레드 대기 중
...
[Thread-200] NexonDataCollector: 타임아웃 — 스레드 대기 중
[Thread-201] Tomcat: 스레드 풀 고갈 — 요청 대기
[Thread-202] Tomcat: 스레드 풀 고갈 — 요청 거부
```

**1단계: 외부 API 타임아웃**
Nexon API가 응답하지 않는다. WebClient는 타임아웃될 때까지 스레드를 붙잡는다.

**2단계: 스레드 풀 고갈**
모든 Tomcat 스레드가 Nexon API 응답을 기다린다. 새 요청을 받을 스레드가 없다.

**3단계: 커넥션 풀 포화**
대기 중인 스레드들은 각자 DB 커넥션을 물고 있다. 커넥션 풀이 포화된다.

**4단계: 전체 서비스 마비**
DB 커넥션이 없으니 캐시 조회도 안 된다. 인증도 안 된다. 아무것도 안 된다.

하나의 외부 API 장애가 전체 시스템을 마비시키는 완벽한 도미노였다.

---

## 장애 타임라인

```text
00:00  Nexon API 응답 지연 시작 (50ms → 500ms)
00:30  응답 시간 2초 돌파. 일부 요청 타임아웃
01:00  Tomcat 스레드 풀 고갈 시작 (200/200 사용 중)
01:30  HikariCP 커넥션 풀 포화 (25/25 사용 중)
02:00  전체 서비스 마비. 모든 엔드포인트 503 반환
??     Nexon API 정상 복구 (정확한 시간 불명 — 모니터링 없음)
??     서비스 자연 복구 (추정: 02:30 이전)
```

전체 장애 시간은 추정할 수조차 없었다. 모니터링이 없었으니까.

## 근본 원인: 4가지 기술 부채

### 1. 장애 격리 부재

```java
// 당시의 코드 — 타임아웃은 있지만 격리는 없다
public NexonApiCharacterData fetch(String ocid) {
    return webClient.get()
        .uri("/character/basic?ocid={ocid}", ocid)
        .retrieve()
        .bodyToMono(NexonApiCharacterData.class)
        .block(); // ← 무한 대기 가능
}
```

`block()` 호출은 스레드를 붙잡는다. 타임아웃 설정이 있었지만, 기본값은 30초였다. 30초 동안 하나의 스레드가 블록되면, 200개의 스레드가 순식간에 고갈된다.

### 2. Fallback 미구현

Nexon API가 죽었을 때 보여줄 대체 응답이 없었다. 캐시된 데이터를 보여주거나, "일시적으로 사용할 수 없습니다"라는 안내를 보여주는 대신, 그냥 에러를 반환했다.

### 3. 리소스 고갈 방지 없음

외부 API 호출에 대한 동시성 제한이 없었다. 1,000개의 요청이 동시에 들어오면 1,000개의 스레드가 동시에 외부 API를 호출했다.

### 4. 모니터링 부족

외부 API 응답 시간, 에러율, 서킷 상태 — 아무것도 측정하지 않았다. 장애가 발생해도 알 수 없었다.

## 장애대응 테스트로 재현

나중에 이 시나리오를 장애대응 테스트 Scenario 12 **Gray Failure**로 재현했다.

```
장애대응 테스트 결과 — Gray Failure

P95 Latency: 50ms → 450ms (9배 증가)
P99 Latency: 100ms → 2,000ms (20배 증가)
Error Rate: 0% → 15% (HTTP 5xx)
Throughput: 1,000 req/s → 150 req/s (85% 감소)

서킷 브레이커: 에러율 15%에서 TRIPPED ✅
```

재현은 성공적이었다. 불행히도 "성공적"이라는 건 "똑같이 망가졌다"는 뜻이었다.

하지만 이번에는 달랐다. 서킷 브레이커가 에러율 15%에서 트립했다. 15%의 요청은 실패했지만, 나머지 85%는 정상 동작했다. 이전에는 100%가 마비되었던 것과 비교하면 천지 차이였다.

## 교훈

**1. 외부 의존성은 항상 실패한다.**

Nexon API는 우리가 제어하지 않는다. 언제든 느려지거나 죽을 수 있다. 이것을 전제로 설계해야 한다.

**2. 장애는 격리되어야 한다.**

한 컴포넌트의 장애가 다른 컴포넌트로 전파되면 안 된다. 외부 API 장애가 전체 서비스를 마비시키는 구조는 잘못되었다.

**3. 측정하지 않으면 개선할 수 없다.**

장애 지속 시간조차 알 수 없었다. 모니터링은 선택이 아니라 필수다.

**4. Fallback은 있어야 한다.**

완벽한 응답을 줄 수 없더라도, "지금 서비스가 불안정합니다"라도 보여줘야 한다. 에러 페이지보다는 낫다.
