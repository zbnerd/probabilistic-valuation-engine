# 12장: 완성 — 7,347 RPS, 실패가 만든 성과

> "성과는 숫자가 아니다. 숫자는 결과일 뿐이다. 진짜 성과는 과정에 있다."

---

## 여정의 숫자

2026년 1월 20일부터 3월 30일까지, 10주간의 여정.

> **측정 환경:** RPS는 성공한 요청만 계산합니다. 7,347 RPS는 캐시 웜업 완료 후 200K-300K rows 실제 데이터 기준, 10,994 RPS는 빈 DB 기준입니다.
> **33% 차이 원인:** 빈 DB에서의 10,994 RPS는 이상적 최대치이며, 실데이터 환경(200K-300K rows)에서는 캐시 invalidation 증가, DB upsert 비용 상승, CPU pipeline 포화 등으로 인해 7,347 RPS로 자연스럽게 하락합니다.

| 메트릭 | 시작 (1월 20일) | 완성 (3월 30일) | 변화 |
|--------|----------------|----------------|------|
| RPS | 97 | 7,347 (실제 운영), 10,994 (빈 DB 기준) | **76배** / 113배 |
| p99 지연 | 4,100ms | 36ms | **-99%** |
| 에러율 | 59.7% | 0% | **완전 제거** |
| 데이터베이스 | 3개 (MySQL+Redis+MongoDB) | 1개 (PostgreSQL) | **-67%** |
| 커넥션 풀 | 89+ connections | 25 connections | **-72%** |
| Outbox 파일 | 42개 | 0개 (PGMQ 통합) | **-100%** |
| 장애대응 테스트 | 0개 | 34개 시나리오 (정규 16 + 극한 18) | **무한 증가** |
| 가드레일 | 0개 | 88개 패턴 | **무한 증가** |

## 76배의 비밀

76배의 성능 향상은 한 번의 마법이 아니었다. 매 단계에서 조금씩, 측정하면서, 개선했다.

```
97 RPS     (시작)
  ↓ 장애대응 테스트 베이스라인
223 RPS    (+130%)
  ↓ L1 Fast Path (직렬화 제거)
555 RPS    (+149%)
  ↓ Write-Behind Buffer (비동기 DB 쓰기)
674 RPS    (+21%)
  ↓ Parallel Presets (프리셋 병렬 계산)
965 RPS    (+43%)
  ↓ Stateless Tradeoff (일관성 ↔ 속도)
325 RPS    (-66%) ← 후진. 하지만 올바른 선택
  ↓ Auto Warmup + 복구
940 RPS    (+189%)
  ↓ PostgreSQL NOTIFY + Micro-Batching
10,994 RPS (빈 DB 기준)
  ↓ 실제 데이터 (200K-300K rows)
7,347 RPS  (실제 운영 환경)
```

### "후진"이 필요했던 이유

965 RPS에서 325 RPS로 떨어진 단계가 있다. 이건 버그가 아니었다. **의도적인 선택**이었다.

캐시 일관성과 속도 사이의 트레이드오프. 빠르지만 일관성이 없는 것 vs 느리지만 일관성이 있는 것. 우리는 일관성을 선택했다. 965 RPS의 3분의 1로 떨어지더라도.

그리고 Auto Warmup으로 복구했다. 일관성을 유지하면서 속도도 되찾았다.

## 실패가 만든 것들

### 서킷 브레이커 — 외부 API 장애의 결과

1장의 도미노 장애가 없었다면 서킷 브레이커는 도입되지 않았을 것이다. 323회의 트립 기록은 323회의 방어 성공이다.

### TieredCache + SingleFlight — 캐시 스탬피드의 결과

100개의 동일한 쿼리가 DB를 때린 날이 없었다면, Leader/Follower 패턴은 구현되지 않았을 것이다.

### PGMQ — 이중 쓰기의 고통의 결과

42개의 Outbox 파일이 고통이 아니었다면, PostgreSQL 네이티브 큐는 고려되지 않았을 것이다.

### LogicExecutor — try-catch 남용의 결과

에러를 삼키는 코드가 만연하지 않았다면, 7가지 실행 패턴은 탄생하지 않았을 것이다.

### 알림 격리 — 침묵의 경보의 결과

장애 중에 알림마저 죽는 경험을 하지 않았다면, Stateless 알림은 구현되지 않았을 것이다.

## 측정의 철학

이 여정에서 가장 중요한 원칙은 하나였다:

**"측정하지 않으면 개선할 수 없다."**

모든 최적화는 측정에서 시작했다. 그리고 측정으로 검증했다.

### 측정한 것들

```
성능:
  - RPS (초당 요청 수)
  - p50/p95/p99 지연 시간
  - 에러율

리소스:
  - 커넥션 풀 사용률
  - 스레드 풀 사용률
  - GC 오버헤드
  - 힙 사용량

캐시:
  - 캐시 히트율 (목표: >99%)
  - DB Query Ratio (목표: <1%)
  - SingleFlight Fallback Rate (목표: <1%)

안정성:
  - 서킷 브레이커 상태
  - 락 경합률
  - 재시도 성공률
```

### 측정하지 않은 것들

```
"빨라졌을 것 같다"  ← 주관적 판단. 금지.
"최적화했으니 괜찮겠지" ← 근거 없는 낙관. 금지.
"비슷할 거야" ← 비교 불가. 금지.
```

```

  Client
    ↓

  MySQL  Redis  MongoDB
    ↑       ↑
```

## 교훈

**1. 장애는 선생님이다.**

모든 장애가 시스템을 단단하게 만들었다. 장애를 피하지 말고, 장애에서 배우라.

**2. 단순함이 강함이다.**

3개의 데이터베이스를 1개로 줄인 것이, 어떤 알고리즘 최적화보다 큰 성과를 냈다.

**3. 측정이 진실이다.**

"빠르다", "느리다"가 아니라 "7,347 RPS", "36ms p99". 숫자가 진실이다.

**4. 가드레일은 미래의 선물이다.**

88개의 가드레일은 과거의 실수가 미래의 개발자에게 주는 선물이다. "이건 하지 마라"는 경고가 아니라 "이미 해결한 문제"라는 안내.

**5. 여정은 끝나지 않는다.**

7,347 RPS는 끝이 아니다. CPU 프로파일링, JSON 부분 파싱, Changed-only Upsert — 아직 할 일이 많다.
