## 1. 현재 성능 조건과 가정

### 1.1 실측 성능 수치

| 지표 | 수치 | 조건 | 비고 |
|------|------|------|------|
| **RPS** | **7,347** | 200K~300K rows, 단일 인스턴스 | 실 운영 데이터 기반 |
| **RPS (이상적)** | 10,994 | 빈 DB | 현실적이지 않음 |
| **p99 지연시간** | 36ms | 캐시 히트 경로 | 캐시 미스는 100-500ms |
| **캐시 히트율** | ~98% | 인기 캐릭터 위주 트래픽 | Long-tail 트래픽에서는 80-90% |
| **인스턴스 수** | 1 (단일) | 모든 테스트 기준 | Scale-out은 준비만 완료 |

### 1.2 핵심 가정

1. **인기 캐릭터 중심 트래픽**
   - 상위 100개 캐릭터가 전체 트래픽의 80% 차지
   - Long-tail(1회 조회 캐릭터)이 20% 미만
   - 이 가정이 깨지면 캐시 히트율 급락

2. **단일 인스턴스 운영**
   - 현재 모든 성능 수치는 단일 인스턴스 기반
   - LISTEN/NOTIFY로 다중 인스턴스 캐시 무효화는 구현됨
   - 하지만 실제 2~4 인스턴스로 선형 확장 검증은 안 됨

3. **Fan-Out 보호 구현 완료**
   - GlobalAdmissionControl으로 폭증 트래픽 차단 가능
   - 현재는 비활성화 상태
   - "보호막은 폭풍이 오기 전에 설치해야 한다"

### 1.3 빈 DB vs 실데이터 격차

```
빈 DB (10,994 RPS)
  ↓
실데이터 200K~300K rows (7,347 RPS)
  ↓
33% 성능 하락
```

**하락 원인:**
- 캐시 미스 시 DB 왕복 (JSON 파싱 300KB)
- B-Tree 인덱스 탐색 비용
- UNLOGGED TABLE 쓰기 경합

**교훈:** 빈 DB 벤치마크는 자랑거리가 아니다. 7,347 RPS가 진짜다.

## 2. 왜 50+ 인스턴스에서는 설계에 한계가 있는가

### 2.1 PostgreSQL NOTIFY 브로드캐스트 한계

현재 캐시 무효화는 PostgreSQL LISTEN/NOTIFY 기반:

```kotlin
// 단일 인스턴스 → 알림 1회
NOTIFY cache_invalidation, 'character:123'

// 50 인스턴스 → 알림 50회 복제
NOTIFY cache_invalidation, 'character:123'
  → Instance 1 receives
  → Instance 2 receives
  → ...
  → Instance 50 receives
```

**문제점:**
- 50개 인스턴스에 동일 알림 브로드캐스트
- PostgreSQL → 네트워크 → 애플리케이션 50회 전송
- 캐시 무효화 빈도가 높으면 네트워크 병목

### 2.2 Advisory Lock Connection Pool 경합

```kotlin
// 단일 인스턴스: Lock 획득 시도 1회
pg_try_advisory_lock(123)

// 50 인스턴스: Lock 획득 시도 50회
Instance 1: pg_try_advisory_lock(123) → SUCCESS
Instance 2: pg_try_advisory_lock(123) → FAIL (retry)
Instance 3: pg_try_advisory_lock(123) → FAIL (retry)
...
Instance 50: pg_try_advisory_lock(123) → FAIL (retry)
```

**문제점:**
- 49개 인스턴스가 Lock 획득 실패 후 재시도
- PostgreSQL Connection Pool 경합
- 단일 DB에서 수천 커넥션 발생

### 2.3 PGMQ Polling 경합

```kotlin
// 1개 워커: PGMQ read() 1회/초
FOR msg IN pgmq.read('calculation_queue', 10, 1) LOOP
  -- process
END LOOP

// 50개 워커: PGMQ read() 50회/초
Worker 1: pgmq.read() → SELECT ... LIMIT 1
Worker 2: pgmq.read() → SELECT ... LIMIT 1
...
Worker 50: pgmq.read() → SELECT ... LIMIT 1
```

**문제점:**
- 50개 워커가 동일 테이블 폴링
- SELECT FOR UPDATE SKIP LOCKED 경합
- DB CPU 사용량 폭증

### 2.4 해결 방안 vs 비용

| 해결 방안 | 효과 | 비용 | 도입 시점 |
|----------|------|------|-----------|
| **Redis Pub/Sub** | 브로드캐스트 O(1) | Redis 인프라 추가 | 20+ 인스턴스 |
| **Kafka Partition** | 파티션 수 = 선형 확장 | Kafka 클러스터 | 50+ 인스턴스 |
| **PgBouncer** | 커넥션 풀링 | 인프라 설정 | 10+ 인스턴스 |
| **현재 유지** | 단일 DB 운영 | 없음 | 10인스턴스 미만 |

**ADR-324 Scale-out Strategy 결론:**
> "10인스턴스 미만에서는 PostgreSQL 단일 DB로 충분. 그 이상은 Redis/Kafka 재도입 고려."

## 3. Redis 재도입 조건

현재 PostgreSQL 단일 DB로 충분하지만, 다음 조건에서는 Redis 재도입 고려.

### 3.1 L2 캐시 읽기 병목

**증상:**
- PostgreSQL UNLOGGED TABLE 읽기 지연 p99 > 50ms
- `cache_storage` 테이블 SELECT 지연 증가
- Vacuum/Autovacuum 빈도 증가

**원인:**
- UNLOGGED TABLE도 결국 Disk I/O
- 10K+ RPS에서 Disk seek 경합

**해결:**
- Redis 메모리 캐시로 L2 이관
- PostgreSQL은 영속성 저장소만 담당

### 3.2 50+ 인스턴스

**증상:**
- LISTEN/NOTIFY 브로드캐스트 지연 p99 > 100ms
- Advisory Lock 경합으로 Lock 획득 실패율 > 10%

**원인:**
- PostgreSQL 네트워크 브로드캐스트 한계
- 단일 DB Connection Pool 한계

**해결:**
- Redis Pub/Sub으로 캐시 무효화
- Redisson Distributed Lock으로 Advisory Lock 대체

### 3.3 실시간 푸시 필요

**현재:** 폴링 기반 (클라이언트가 결과를 주기적으로 조회)

```
Client: GET /api/v2/calculation/123 (PENDING)
Client: GET /api/v2/calculation/123 (PENDING)
Client: GET /api/v2/calculation/123 (COMPLETED) ← 3초 후
```

**개선:** Server-Sent Events 또는 WebSocket

```
Client: SSE 연결
Server: 계산 완료 시 즉시 푸시
```

**Redis 필요성:**
- Pub/Sub으로 실시간 이벤트 전파
- Connection Store (WebSocket 세션 관리)

### 3.4 Rate Limit 분산

**현재:** 인스턴스별 Local Rate Limit

```kotlin
// Instance 1: 1분에 100회 제한
// Instance 2: 1분에 100회 제한
// → 전체 200회 가능 (회피 가능)
```

**개선:** Redis Centralized Rate Limit

```kotlin
// Redis: IP별 카운터
INCR rate_limit:192.168.1.1
EXPIRE rate_limit:192.168.1.1 60
```

### 3.5 재도입 결정 매트릭스

| 조건 | 임계값 | 재도입 필요성 |
|------|-----------------------|
| L2 캐시 지연 p99 | > 50ms | 높음 |
| 인스턴스 수 | > 50 | 높음 |
| 실시간 푸시 요구사항 | 있음 | 높음 |
| Rate Limit 회피 공격 | 발생 | 중간 |
| 월 트래픽 비용 | > $500 | 중간 |

## 4. 남은 병목 지점

### 4.1 단일 인스턴스만 검증

**현황:**
- 현재 모든 테스트는 단일 인스턴스 기반
- LISTEN/NOTIFY로 다중 인스턴스 캐시 무효화는 구현됨
- 하지만 실제 2~4 인스턴스로 선형 확장 검증 필요

**검증 필요 항목:**
- [ ] 2인스턴스 부하 테스트 (합계 14,694 RPS 달성?)
- [ ] 4인스턴스 부하 테스트 (합계 29,388 RPS 달성?)
- [ ] Cache Inconsistency 발생 여부
- [ ] Lock Starvation 발생 여부

**관련 ADR:** ADR-324: Scale-out Strategy

### 4.2 Fan-Out Explosion (아직 발생 안 함)

**시나리오:** 1,000 users × 1,000 different keys

```
User 1: GET /api/v2/expectation?key=abc123
User 2: GET /api/v2/expectation?key=def456
...
User 1000: GET /api/v2/expectation?key=zzz999
```

**분석 결과:**
- CPU 즉시 포화 (Cache Miss 100%)
- 모든 요청이 DB 조회 → JSON 파싱 → 계산
- GlobalAdmissionControl 없으면 시스템 붕괴

**현재 상태:**
- GlobalAdmissionControl 구현 완료
- 비활성화 상태 (폭풍이 오기 전에 설치)
- Issue #617: Admission Control

### 4.3 JSON Parsing CPU Overhead

**현황:**
- 300KB JSON 파싱이 CPU의 25~30% 차지 (추정)
- async-profiler로 실제 핫스팟 측정 아직 필요

**해결 후보:**
1. Jackson Streaming Parser로 필요 필드만 추출
2. Protocol Buffers로 JSON 대체
3. JSON Partial Parsing (PR #752: parseSinglePreset()으로 3x 파싱 속도 개선)

**기대 효과:**
- CPU 25% → 10% 감소
- RPS 7,347 → 10,000+ 향상

### 4.4 Virtual Thread Limitation

**PR #746: Virtual Thread → FixedThreadPool 환원**

**원인:**
```kotlin
synchronized(lock) {
    // blocking 작업
    // → carrier thread pinning 발생
}
```

**해결:**
- ReentrantLock으로 전환 후 재도전 가능
- 현재: 플랫폼 스레드 기반으로 안정 운영

### 4.5 Cache Warming Gap

**현황:**
- Auto Warmup이 인기 캐릭터 100개만 사전 캐시
- Cold Start 시 첫 요청은 여전히 느림 (p99 500ms+)

**해결 후보:**
1. 스케줄러 패턴 기반 사전 캐시 확대
2. 점진적 워밍업 (Tiered Warmup)
3. 예측적 캐시 (ML 기반 인기 캐릭터 예측)

### 4.6 No Real-Time Push

**현재:** 폴링 기반

```
Client: GET /api/v2/calculation/123 (PENDING)
Client: GET /api/v2/calculation/123 (PENDING)
Client: GET /api/v2/calculation/123 (COMPLETED) ← 3초 후
```

**해결 후보:**
1. Server-Sent Events (SSE)
2. WebSocket
3. Redis Pub/Sub 기반 푸시

### 5.1 Priority 1: CPU Profiling (async-profiler)

**목표:** 실제 핫스팟 측정

```bash
# async-profiler로 CPU Flamegraph 생성
./profiler.sh -d 30 -f cpu-flamegraph.html <pid>

# JSON 파싱이 정말 25-30%인지 확인
./profiler.sh -d 30 -e alloc:*:GZIPInputStream <pid>
```

**기대 효과:**
- 추측이 아닌 실측 기반 최적화
- JSON 파싱 vs DB 조회 vs Network I/O 비중 정확히 파악

### 5.2 Priority 2: JSON Partial Parsing

**현재:** 300KB 전체 파싱

```kotlin
val objectMapper = ObjectMapper()
val fullJson = objectMapper.readTree(jsonString) // 300KB 전체 파싱
val cubeData = fullJson.get("cube")
```

**개선:** 필요 필드만 추출

```kotlin
// Jackson Streaming API
val parser = objectMapper.getFactory().createParser(jsonString)
while (parser.nextToken() != null) {
    val fieldName = parser.currentName()
    if (fieldName == "cube") {
        // cube 필드만 파싱
    }
}
```

**기대 효과:**
- CPU 25% → 10% 감소
- RPS 7,347 → 10,000+ 향상

### 5.3 Priority 3: Changed-Only Upsert

**현재:** 전체 필드 업데이트

```sql
INSERT INTO character_valuation_views (ocid, full_data)
VALUES ('ocid123', '<300KB JSON>')
ON CONFLICT (ocid) DO UPDATE SET
  full_data = EXCLUDED.full_data;
```

**개선:** Dirty Tracking

```kotlin
val dirtyFields = DirtyTracker.track(character) {
    it.cube.presetNo = 456
    // 다른 필드는 변경 안 함
}

// 변경된 필드만 업데이트
UPDATE character_valuation_views
SET cube_data = jsonb_set(full_data, '{cube,presetNo}', '456')
WHERE ocid = 'ocid123';
```

**기대 효과:**
- Write 30-50% 감소
- DB Disk I/O 감소
- Vacuum 부하 감소

### 5.4 Priority 4: Global Admission Control 활성화

**현재:** 비활성화 상태

```yaml
maple:
  infra:
    admission:
      enabled: false  # → true로 변경
      maxConcurrent: 100
```

**활성화 효과:**
- Fan-Out Explosion 방어
- 시스템 붕괴 방지
- Graceful Degradation

### 5.5 Priority 5: 2~4 인스턴스 실증

**목표:** 선형 확장 검증

```
1 Instance: 7,347 RPS
2 Instances: 14,694 RPS (2x)
4 Instances: 29,388 RPS (4x)
```

**검증 항목:**
- [ ] Cache Inconsistency 0건
- [ ] Lock Starvation 0건
- [ ] Deduplication Rate > 90%

### 5.6 Priority 6: PgBouncer 도입

**목표:** 커넥션 풀 병목 해소

```ini
[pgbouncer]
pool_mode = session
max_client_conn = 1000
default_pool_size = 50
```

**기대 효과:**
- 앱 1000 커넥션 → PgBouncer 50 커넥션으로 멀티플렉싱
- PostgreSQL 커넥션 경합 해소
- 처리량 2-3x 향상

**관련 ADR:** ADR-pgmq-kafka-migration

### 5.7 Priority 7: Kotlin Coroutine 확대

**현재:** CompletableFuture + Executor

```kotlin
val future1 = CompletableFuture.supplyAsync { calc1() }
val future2 = CompletableFuture.supplyAsync { calc2() }
CompletableFuture.allOf(future1, future2).join()
```

**개선:** Kotlin Coroutine

```kotlin
coroutineScope {
    val result1 = async { calc1() }
    val result2 = async { calc2() }
    awaitAll(result1, result2)
}
```

**기대 효과:**
- 코드 가독성 향상
- Virtual Thread와 시너지
- Structured Concurrency 보장

## 6. 장기 아키텍처 비전

### 6.1 Phase 7 (완료): Stateful 제거 + Multi-Module

```
Before (Stateful):
┌─────────────────────────────────────────┐
│  Single Instance (Stateful)             │
│  ├── In-Memory SingleFlight             │
│  ├── Redis Buffer                       │
│  └── MySQL + MongoDB + Redis            │
└─────────────────────────────────────────┘

After (Stateless):
┌─────────────────────────────────────────┐
│  Multi-Instance (Stateless)             │
│  ├── PostgreSQL Single Flight           │
│  ├── PostgreSQL L2 Cache                │
│  └── PostgreSQL only                    │
└─────────────────────────────────────────┘
```

### 6.2 Phase 8-A: Kafka + Debezium CDC

**시점:** 트래픽이 현재 대비 5배 증가하고, DB Outbox Polling이 병목이 될 때

**목표:** DB 기반 Outbox Polling을 Kafka 기반 이벤트 버스로 전환

```
Before (DB Polling):
Service → Outbox Table → Polling (1s) → Publisher → Kafka

After (CDC):
Service → Outbox Table → Debezium (Binlog) → Kafka
```

**장점:**
- Real-time 이벤트 전송 (CDC 기반)
- DB 부하 제로 (Binlog only 읽기)
- Consumer 독립 확장 가능

**관련 ADR:** ADR-pgmq-kafka-migration

### 6.3 Phase 8-B: Calculation Engine 독립 분리

**시점:** 특정 도메인에 부하가 쏠리는 현상 발생 시

**목표:** 부하가 집중되는 모듈을 독립 서비스로 분리

```
Before (Monolith):
┌─────────────────────────────────────────┐
│  maple-app                              │
│  ├── Query Server                       │
│  ├── Worker Server                      │
│  └── Calculation Engine (CPU 80%+)      │ ← 병목
└─────────────────────────────────────────┘

After (MSA):
┌──────────────────┐          ┌──────────────────┐
│  maple-app       │          │  maple-calc      │
│  (Query + Worker)│  Kafka   │  (Independent)   │
│                  │─────────>│                  │
│  CPU 20%         │  Topic   │  CPU 80%         │
└──────────────────┘          └──────────────────┘
```

### 6.4 Phase 8-C: 완전 MSA (필요 시)

**시점:** 트래픽이 현재 대비 10배 이상, 여러 팀이 협업하는 규모

**철학:**
> "MSA는 처음부터 하는 것이 아니라, **잘 정리된 Monolith를 필요한 만큼만 찢어가는 것**"

**전제 조건:**
- [ ] Clean Architecture 완료
- [ ] Pragmatic CQRS 구현
- [ ] Event-Driven Communication 패턴 확립
- [ ] Service Boundary 명확히 정의

## 7. 솔직한 현실 인정

### 7.1 이 프로젝트의 실제 트래픽

**설계 트래픽:** 5-20 QPS (실운영 기준)

**부하 테스트 수치:** 7,347 RPS (367배 차이)

**의미:**
- 7,347 RPS는 부하 테스트 수치, 실제 트래픽은 훨씬 적음
- "오버엔지니어링을 의심하라" — 5-20 QPS에 분산 버퍼+메시지 큐는 과한 것일 수 있음

### 7.2 하지만 문제를 이미 알고 있으므로

**오버엔지니어링이 아닌 이유:**
1. 문제를 이미 알고 있음 (Fan-Out, Cache Inconsistency, Lock Starvation)
2. 실제 필요 시점에 구축 가능 (Architecture Decision Record가 있음)
3. 단순함을 유지하면서도 확장 가능한 구조

**가장 큰 자산:**
> 숫자가 아니라 **의사결정의 과정**

- ADR로 모든 결정을 기록
- 트레이드오프를 명시
- 롤백 전략을 준비

### 7.3 인터뷰 활용 전략

**Q: "Redis 제거했는데, 다시 도입할 생각 없나?"**

**A:**
> "현재는 PostgreSQL 단일 DB로 충분합니다. 7,347 RPS를 단일 인스턴스로 달성했으니까요.
>
> 하지만 **다음 조건에서는 Redis 재도입을 고려할 것입니다.**
>
> 1. **L2 캐시 읽기 병목**: PostgreSQL UNLOGGED가 읽기 한계 도달 시
> 2. **50+ 인스턴스**: LISTEN/NOTIFY가 브로드캐스트 한계 도달 시
> 3. **실시간 푸시 필요**: WebSocket/SSE 도입 시 Pub/Sub 필요
>
> 제 경험은 **'기술을 도입한 경험'**이 아니라, **'언제/왜 도입해야 하는지 아는 경험'**입니다."

**Q: "MSA 경험 있으신가요?"**

**A:**
> "MSA는 처음부터 하는 것이 아니라, **잘 정리된 Monolith를 필요한 만큼만 찢어가는 것**이라고 생각합니다.
>
> 저는 이미 **4개 모듈**을 분리했고, **Clean Architecture** 적용으로 모듈 간 결합도를 최소화했습니다. 또한 **CQRS** 패턴으로 조회/처리 서버 분리 계획도 세워두었습니다 (ADR-013).
>
> 이렇게 **'찢을 준비가 된 Monolith'**가, 섣불리 MSA로 나눈 것보다 훨씬 안정적이고 확장 가능하다고 생각합니다."

## 8. 요약

### 8.1 현재 상태

| 항목 | 상태 | 비고 |
|------|------|------|
| **RPS** | 7,347 | 200K~300K rows, 단일 인스턴스 |
| **p99 지연** | 36ms | 캐시 히트 경로 |
| **캐시 히트율** | ~98% | 인기 캐릭터 위주 |
| **인스턴스** | 1 (단일) | Scale-out 준비만 완료 |
| **인프라** | PostgreSQL only | 3 → 1 간소화 |

### 8.2 주요 한계

1. **단일 인스턴스만 검증** — 다중 인스턴스 선형 확장 실증 필요
2. **Fan-Out Explosion 미발생** — 보호 장치는 설치됨, 실증 안 됨
3. **JSON Parsing 병목** — CPU 25~30% 차지 (추정)
4. **Virtual Thread 미사용** — Carrier thread pining 이슈
5. **Cache Warming Gap** — Cold Start 시 느림
6. **No Real-Time Push** — 폴링 기반만 구현

### 8.3 Redis 재도입 조건

| 조건 | 임계값 | 재도입 필요성 |
|------|--------|---------------|
| L2 캐시 지연 p99 | > 50ms | 높음 |
| 인스턴스 수 | > 50 | 높음 |
| 실시간 푸시 요구사항 | 있음 | 높음 |
| Rate Limit 회피 공격 | 발생 | 중간 |

### 8.4 다음 최적화 우선순위

1. CPU Profiling (async-profiler)
2. JSON Partial Parsing
3. Changed-Only Upsert
4. Global Admission Control 활성화
5. 2~4 인스턴스 실증

### 8.5 장기 비전

```
Phase 7 (완료): Stateful 제거 + Multi-Module
Phase 8-A: Kafka + Debezium CDC (트래픽 5배 증가 시)
Phase 8-B: Calculation Engine 독립 분리
Phase 8-C: 완전 MSA (필요 시)
```

### 8.6 솔직한 인정

- 이 프로젝트는 **5-20 QPS 실운영 트래픽**에 설계됨
- 7,347 RPS는 부하 테스트 수치, 실제 트래픽은 훨씬 적음
- "오버엔지니어링을 의심하라" — 5-20 QPS에 분산 버퍼+메시지 큐는 과한 것일 수 있음
- 하지만 문제를 이미 알고 있으므로, 실제 필요 시점에 구축 가능
- 가장 큰 자산은 숫자가 아니라 **의사결정의 과정**

## 9. 마지막 조언

### 9.1 채용 담당자/면접관에게

이 프로젝트에서 보여줄 수 있는 것:
1. **측정 기반 사고**: 97 RPS → 7,347 RPS (76배)를 단계별로 측정하며 개선
2. **트레이드오프 명시**: 속도 vs 정합성, 단순함 vs 확장성
3. **롤백 전략**: 모든 주요 결정에 롤백 기준 마련
4. **문서화**: ADR로 모든 결정을 기록
5. **솔직함**: 한계를 인정하고, 언제/왜 개선해야 하는지 아는 것

### 9.2 동료 개발자에게

성능 최적화의 핵심:
1. **측정하고, 추측하지 마라**
2. **단순함이 성능이다**
3. **트레이드오프를 명시하라**
4. **현실에서 측정하라**
5. **오버엔지니어링을 의심하라**

### 9.3 미래의 나에게

이 문서를 다시 읽을 때가 오면:
- Redis 재도입했는가? → 그렇다면, 어떤 조건에서 도입했는가?
- Kafka 도입했는가? → 그렇다면, DB Polling이 병목이 되었는가?
- MSA로 분리했는가? → 그렇다면, 단일 Monolith로는 부족했는가?

**기억할 것:**
> "완벽해 보이는 시스템보다, 한계를 아는 시스템을 신뢰한다."
