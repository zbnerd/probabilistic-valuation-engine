## 2. 재측정·추가 증거가 필요한 성과

### 과거 7,347 RPS

- 기존 이력서의 `97→7,347 RPS, 76배` 문구는 사용하지 않았다. 두 수치는 버전·workload·DB rows·connection·cache state가 같은 실험이 아니다.
- `docs/06_Performance_Journey/09_postgresql_notify.md`에는 첫 7,347 RPS 측정의 errors 65가 있고, `10_real_data_challenge.md`에는 2026-03-24 후속 측정 `wrk -t4 -c200 -d120s`, DB 200k~300k rows, 7,347 RPS/p99 36ms/errors 0이 있다.
- raw wrk stdout, host CPU/RAM, commit SHA, endpoint/request corpus, cache warm/cold 비율이 없다. 이 자료를 확보하거나 같은 조건으로 재측정하기 전에는 headline/개선률에서 제외하는 편이 안전하다.
- 본문 임시 문구: “과거 프로젝트 문서에 후속 absolute 측정이 보고됐으나 raw artifact 부족으로 현재 성능·76배 개선 근거로 사용하지 않았다.”

### single-writer hot path 개선

- ITEM_EQUIPMENT phase의 보고서상 약 80시간 관측 창에서 queue 3,000, submit 1.3~1.7s, 35초 queue-depth 순감소율 약 71 records/s라는 병목 근거는 있다. 다만 external-api/calculator uptime은 80h14m, synchronizer/cleanup은 71h11m이다.
- 보고서의 `lifetime avg 136.57`은 38.08M/80h14m 단순 산술값 약 131.84와 불일치하므로 raw Prometheus query/window를 확인할 때까지 완성본에서 제외했다.
- producer-side serialization과 upload-success callback은 보고서상 약 80시간 관측 창 전에 이미 적용돼 있었다. 이 관측은 두 변경의 before가 아니며, 관측 당시 병목 경계는 single consumer의 gzip/chunk-close·async upload 등록 경로다.
- `BEST_SPEED`만 보고서 commit 뒤에 적용됐지만 동일 commit·동일 서버·동일 데이터·동일 window의 after benchmark가 없다.
- ADR-729의 ≥150 files/s는 target이며 `Observed Result: TBD`다. PR #1452는 closed-unmerged다.
- 후속 권장: commit SHA, Contabo 8 cores/23GB/600Mbps, 같은 ITEM_EQUIPMENT corpus·rate/in-flight 250, 30분 warm-up 뒤 최소 2시간의 before/after를 각각 3회 수집하고 users/s·queue depth·sink submit p95/p99·CPU·GC를 함께 보존.

### dual orchestration 수정

- 03:00 처리 중단은 06-25·06-26 두 번이다. 06-26은 slot race를 직접 확인했고, 06-25는 보고서가 같은 원인의 다른 발현으로 소급 추정한다.
- PR #1433/ADR-736으로 legacy cron 제거와 compile/test는 확인됐다.
- ADR은 다음 03:00 runtime validation을 deferred로 남겼고 후속 중복 DAG 제거 PR #1442도 있다.
- “재발 0”을 쓰려면 배포 SHA, 연속 2~3일의 Airflow DAG run, 단일 trigger 로그, phase slot timeline, loop 정상 시작을 보존해야 한다.

### PR #1463 module ownership

- GitHub상 2026-07-20 develop merge, local reachable branch tip은 확인했다. 하지만 현재 checkout HEAD `4da39850b`는 그 branch의 base이고 local `develop`/`origin/develop` ref에는 merge commit이 없다.
- final tip의 direct dependency 3→0은 확인했다. focused tests 86/86, dependency guard, 4 bootJar packaging은 tip 직전 `11ee3c727` 기준이며, final `1f47173e3`의 subscription-constructor 변경을 포함한 rerun은 없다. full/root check, Testcontainers, live Kafka/Docker, load/performance run도 생략됐다.
- 채용 시점의 기본 branch를 fetch한 뒤 merge ancestry와 배포 상태를 다시 확인하고, final-tip-inclusive focused/full test·4 bootJar·smoke evidence를 추가한다.

## 3. 현재 코드에서 반드시 설명할 제한

- 로컬 HEAD의 `ConsumedChunkInbox`는 bounded in-memory queue이고 capacity에서 oldest를 drop한 뒤 Kafka ACK한다. 이 상태를 restart-safe/durable cleanup 또는 end-to-end exactly-once로 소개하지 않는다.
- calculator는 deterministic artifact existence 기반, synchronizer는 DB chunk state/lease 기반으로 멱등 전략이 다르다. “모든 서비스가 하나의 exactly-once 전략”이라고 단순화하지 않는다.
- 82시간 보고서의 `ERROR log 0`과 `failed chunks 0`은 모든 외부 요청 failure 0이라는 뜻이 아니다. expected WARN-level API 실패와 endpoint mismatch skip 2,090건이 별도로 기록돼 있다.
- 82시간 실행은 external-api/calculator/synchronizer 3서비스이며 cleanup은 external-api 내부 scheduler였다. standalone `module-cleanup`은 2026-06-07 이후이므로 현재 4단계 구조와 당시 수치를 같은 시점처럼 설명하지 않는다.
- 보고서상 71시간은 기재 시각으로는 68h27m이다. service process restart 0이지만 처리 loop가 03:00에 두 번 중단되고 수동 개입이 있었다. 두 번째는 dual-orchestration race 직접 확인, 첫 번째는 같은 원인으로 소급 추정이므로 “race 두 번 재현”이라고 쓰지 않는다.
- 보고서상 약 80시간 관측 창의 서비스별 uptime은 80h14m/71h11m으로 다르다. `lifetime avg 136.57`은 산술이 불일치하고, theoretical 41.6/52 users/s 표는 observed 100~150과 단위/window가 섞여 있어 최종 문서에서 제외했다.
- Redis 제거/PostgreSQL-only라는 과거 문구는 현재 V6 cache·urgent dedup·ranking의 Redis 의존과 충돌한다.
- small-file rollup 10~100배는 ADR-743의 proposed/estimated 값이며 구현 성과가 아니다.

## 4. 개인 기여와 AI 활용 문구

- Git/PR author `zbnerd`와 1인 backend 프로젝트는 기여 근거지만 “모든 코드를 보조 없이 혼자 작성”하거나 기여율 100%를 증명하지 않는다.
- 현재 안전 문구: “개인 프로젝트에서 문제 정의, 설계, 구현 acceptance, 검증 기준과 결과 판정을 담당했다. AI로 탐색·초안·반대 관점을 수집하되 actual diff·test·log·metric으로 검증했다.”
- 지원 회사가 생성형 AI 사용 공개를 요구하면 이 문구를 유지한다. 요구하지 않더라도 면접에서 어떤 가설/patch를 기각했는지 설명할 준비가 필요하다.
- 실제 `docs/ai-traces` corpus는 166 sessions/882 files다. 한 JSONL stream은 gzip은 정상이나 line 818~819부터 두 객체가 중첩·중복되어 partial로 처리했다. 세션의 자기평가·완료 선언은 성과 근거로 쓰지 않았다.

## 6. 다음 증거 캡처 체크리스트

1. load/benchmark마다 commit SHA, 시작/종료 timestamp·timezone, hardware, JVM, dataset, endpoint, tool command·raw stdout·Prometheus query/window를 같은 디렉터리에 저장한다.

3. orchestration 수정은 연속 일일 rollover, single trigger, phase slot, loop start/drain까지 확인한다.
