# Technical evidence candidates

## Evidence policy

This document retains only claims that can be checked against current code/config/tests, locally present git objects, or dated measurement documents. Trace summaries are leads only. Quantitative claims must state date/window, environment, load, and collection method; where those are missing, the result is explicitly marked unavailable or rejected.

Contribution attribution is deliberately separate from project outcomes. Commits authored as `zbnerd` are evidence that the repository account authored/merged the change, not proof of unaided work or a percentage contribution. The AI-trace corpus overlaps this period, so a portfolio should describe concrete decisions, reviews, implementation, and verification the candidate can personally explain rather than claim sole authorship.

## 1. Architecture evolution: legacy application to independent pipeline services

**Status: VERIFIED implementation; project-level outcome only.**

- **Problem:** Collection, calculation, synchronization, cleanup, REST, and legacy application concerns could not all share one deployment lifecycle without coupling failures and resource profiles.
- **Cause:** The repository retained a legacy `module-app` while new pipeline stages needed different heap sizes, ports, dependencies, and restart/health policies.
- **Decision:** Extract executable external-api, calculator, synchronizer, REST-controller, and cleanup modules around common/core/infra libraries; deploy the four data-pipeline workers independently.
- **Implementation:** Gradle includes the extracted modules at `settings.gradle:20-36`. `docker-compose.services.yml:15-54`, `docker-compose.services.yml:56-93`, `docker-compose.services.yml:94-133`, and `docker-compose.services.yml:135-172` define independent external-api, calculator, synchronizer, and cleanup containers with distinct ports, heaps, health checks, dependencies, and service identities. Module intent/dependencies are explicit in `module-external-api/build.gradle:1-37`, `module-calculator/build.gradle:1-41`, `module-synchronizer/build.gradle:1-38`, and `module-rest-controller/build.gradle:1-39`.
- **Verification:** Local commit lineage: external-api merge `904ba43899c0fe3dda0fa0ec1bf4866a492b7625` (2026-05-04), calculator `359c613fe5b582569e955f8914a658c7775f1bc7` (2026-05-05), synchronizer `b0d4f33dbed98fe3e7b8a3003c2ed67cd06a453d` (2026-05-10), and four-service containerization `556017399c468a033a55274857d1aedaeb6b8765` (2026-06-22).
- **Quantitative result:** Project-level, not isolated to one extraction commit. The 2026-05-23 22:53–2026-05-27 09:08 run used three extracted services with `-Xms512m/-Xmx1g`, processed 60,190,417 users and 4,034,907,241 items over 82h15m with zero service restarts; counters, process RSS checkpoints, logs, and disk checkpoints are recorded at `docs/endurance-test/endurance-report-82h.md:1-37`, `docs/endurance-test/endurance-report-82h.md:65-102`, and `docs/endurance-test/endurance-report-82h.md:124-160`. Safe claim: designed/implemented/reviewed specific module boundaries and can explain the trade-offs, not “single-handedly built the entire architecture.”

## 2. Storage-backed claim-check and Kafka stage isolation

**Status: VERIFIED.**

- **Problem:** Snapshot and calculation payloads are large (hundreds of records and many item rows per chunk); placing full payloads on Kafka would increase broker/network pressure and bind consumers to producer memory behavior.
- **Cause:** Collection, CPU-heavy calculation, and database projection have different rates and failure modes, but need a durable handoff.
- **Decision:** Store gzip JSONL artifacts in ObjectStorage and publish Kafka events containing identity, counts, and `objectKey` only (claim-check pattern).
- **Implementation:** External-api constructs the artifact key in `module-external-api/src/main/kotlin/maple/externalapi/snapshot/SnapshotSinkEventPublisher.kt:31-69`. Upload completion gates event publication in `module-external-api/src/main/kotlin/maple/externalapi/snapshot/ChunkedSnapshotSink.kt:307-344`. Kafka send completion is represented by a future in `module-external-api/src/main/kotlin/maple/externalapi/snapshot/event/KafkaSnapshotChunkEventPublisher.kt:20-35`. Calculator verifies the source object, derives a deterministic result key, processes under a bounded permit, and treats an existing result as replay/idempotency evidence in `module-calculator/src/main/kotlin/maple/calculator/CalculatorChunkProcessingCoordinator.kt:60-99`. It then awaits Kafka result publication in `module-calculator/src/main/kotlin/maple/calculator/event/KafkaResultEventPublisher.kt:20-31`. Synchronizer consumes the result metadata and passes the object key into its chunk processor at `module-synchronizer/src/main/kotlin/maple/synchronizer/consumer/KafkaResultChunkConsumer.kt:38-93`.
- **Verification:** The focused audit recorded `ChunkedSnapshotSinkTest` passing. Current checkout ancestry includes calculator pipeline `359c613fe5b582569e955f8914a658c7775f1bc7`, synchronizer consumer `b0d4f33dbed98fe3e7b8a3003c2ed67cd06a453d`, common ObjectStorage foundation `e533fc97264cc860929bb0007b7ab78ab4127e5a`, upload-before-publication fix `94cdd5685772570681abc4e58000d57192623b8f`, and PR #1463 artifact lifecycle fix `d440dcd975872896af2d45a4cfc4688a077c2ba4`.
- **Quantitative result:** Project-level long-run evidence only. The May 23–27, 2026, three-service run reports 908GB compressed / 13.31TB uncompressed source data, 94.7GB / 2.10TB results, 120,442 processed chunks, and zero failed chunks (`docs/endurance-test/endurance-report-82h.md:16-49`). Environment/load: three Spring Boot services, daily full runs plus ~47-minute equipment cycles, 1GB max heap per service; metrics came from application counters/logs and host RSS/disk checkpoints (`docs/endurance-test/endurance-report-82h.md:1-6`, `docs/endurance-test/endurance-report-82h.md:51-81`). No direct comparison with payload-in-Kafka was run.
- **Limitations:** The May 82h run predates the June upload/publication fixes above and cannot serve as their long-run regression proof. The older architecture prose at `docs/12_Events/chunk-replay-architecture.md:9-17` still mentions MongoDB and is stale; current projection is PostgreSQL. Exactly-once is not claimed: Kafka delivery is at-least-once, with application idempotency. Object retention/cleanup determines the replay window.
- **Likely candidate contribution:** Commit authorship supports work on the extracted stages and ObjectStorage seam; the long-run result belongs to the whole system and operating environment.

## 3. Data throughput: tune to a measured HTTP pool/rate operating point

**Status: VERIFIED dated observations; no multiplier retained.**

- **Problem:** ITEM_EQUIPMENT fetches were constrained by Reactor Netty connection availability; raising the configured rate alone created pending connections without reaching the target.
- **Cause:** Connection pool, in-flight semaphore, external latency, response size, and downstream writer pressure form a coupled system. The meaningful payload is 200KB+ and CHARACTER_BASIC is not representative.
- **Decision:** Set default pool=150 and rate=250 requests/s, keep both externally configurable, and monitor active/pending connections and body-received latency.
- **Implementation:** The decision and configuration contract are recorded in accepted `docs/01_ADR/ADR-717-external-api-nexon-throughput-tuning.md:9-41`; sensitivity/trade-offs are at `docs/01_ADR/ADR-717-external-api-nexon-throughput-tuning.md:45-73`. Current runtime exposes `max-in-flight` in `module-external-api/src/main/resources/application.yml:39-43` and per-endpoint body/failure metrics in `module-external-api/src/main/kotlin/maple/externalapi/metrics/SnapshotFetchMetrics.kt:13-25`.
- **Verification:** ADR-717 records sampled states rather than a trace completion claim. Commit lineage includes the rate-limiter/pool change surfaced on 2026-06-17 and heap adjustment `a76ff88dd7074ad64bfb018210acd55838a4fec3`.
- **Quantitative result:** On 2026-05-17's ITEM_EQUIPMENT sampling, pool50/rate200 showed ~510ms body average with the pool saturated; pool100/rate200 reached ~200 responses/s; pool150/rate250 produced 51,759 responses over 241s (~215/s) with active=150 and pending=68–83 in early samples (`docs/01_ADR/ADR-717-external-api-nexon-throughput-tuning.md:77-96`). Tooling was application/network-pool metrics and response counters as described by the ADR. Because pool and target rate change together across rows, these are absolute operating points, not a controlled before/after multiplier.
- **Limitations:** A July 2 observation later found sink saturation under a changed pipeline/load (`docs/05_Reports/05_06_Load_Tests/ENDURANCE_THROUGHPUT_CEILING_20260702.md:156-178`). Do not claim that pool tuning permanently removed the system bottleneck or that 215/s equals user throughput across six endpoints.
- **Likely candidate contribution:** Safe claim: performed/tuned the sampled configurations and selected a stable default; system-wide sustained throughput remains a project outcome.

## 4. Caching/read path: partial-hit Redis batch + DB micro-batch + urgent fallback

**Status: VERIFIED implementation; quantitative speedup unavailable.**

- **Problem:** A cache miss per request can amplify Redis/DB round trips and duplicate urgent collection for the same character.
- **Cause:** Concurrent requests arrive within small windows; partial cache hits require retaining hits while batch-querying only misses; a missing read model must not trigger duplicate Kafka work.
- **Decision:** Deduplicate in-flight HTTP requests, drain a bounded buffer every 10ms, use Redis `multiGet`, batch-query PostgreSQL for misses, pipeline cache writes in one RTT, check negative cache, and use Redis SETNX+TTL for urgent-pipeline dedup/status.
- **Implementation:** HTTP in-flight joining and bounded-buffer rejection are in `module-rest-controller/src/main/kotlin/maple/restcontroller/read/ExpectationReadFacade.kt:23-75`. Scheduler drain/shutdown behavior is at `module-rest-controller/src/main/kotlin/maple/restcontroller/read/BatchReadScheduler.kt:34-85` and `module-rest-controller/src/main/kotlin/maple/restcontroller/read/BatchReadScheduler.kt:107-137`. Cache→DB→negative-cache→urgent resolution is at `module-rest-controller/src/main/kotlin/maple/restcontroller/read/BatchResolver.kt:37-116`. Redis partial multi-get and pipelined SETEX are at `module-rest-controller/src/main/kotlin/maple/restcontroller/read/ReadModelCacheService.kt:38-98`; SETNX and status ZSet are at `module-rest-controller/src/main/kotlin/maple/restcontroller/read/UrgentDedupService.kt:35-92`.
- **Verification:** Focused current tests passed: `ExpectationReadFacadeTest` (5), `InflightRequestRegistryTest` (8), and `ReadModelQueryServiceTest` (3). Relevant commits: partial-hit cache `63d30320cfeaf52e5c9ae70f3c158f87382c8129`, pipelined writes `9a8ddb4b94280f088084eb37f7a34e69c36b1583`, negative cache `2406d5069f426bb5db251061be9d1ab7323d1e40`, and service split `cc60d43e28fa8a2cf688728005d887dd0caf1712`.
- **Quantitative result:** **Unavailable for the current V6 implementation.** The code establishes N Redis writes→one pipeline round trip structurally, but no retained dated run provides current endpoint, dataset, concurrency, cache state, hardware, tool, and comparable before/after. Historical 97→7,347 RPS and 10,994 RPS narratives mix versions/data states and are rejected.
- **Limitations:** `BatchResolver` and `ReadModelCacheService` have no direct test classes in the current tree; the audit's initial Gradle filter failed for that reason. Redis is a runtime dependency, contradicting old PostgreSQL-only portfolio language. Inflight HTTP dedup is process-local, while urgent dedup is Redis-backed.
- **Likely candidate contribution:** Commit metadata supports direct work on the V6 path; no performance multiplier should be attributed until a controlled benchmark is captured.

## 5. Concurrency and idempotency: durable chunk claim, lease, state, and ACK ordering

**Status: VERIFIED.**

- **Problem:** Kafka redelivery, concurrent consumers, worker crashes, and state-write races can duplicate database projection or acknowledge work before it is durable.
- **Cause:** An in-memory “currently processing” map cannot survive restart or coordinate replicas; ACK policy depends on durable business state and retry timing.
- **Decision:** Persist each chunk execution under a unique identity, atomically claim it with a lease, classify retryable/terminal failures, release permits in a guaranteed finalizer, and ACK only after terminal/succeeded state is persisted.
- **Implementation:** Migration `module-infra/src/main/resources/db/migration/V128__chunk_execution.sql:1-52` defines payload, status, retry/lease fields, and unique `(execution_type, run_id, endpoint, chunk_id)`. `module-synchronizer/src/main/kotlin/maple/synchronizer/consumer/ChunkConsumerTemplate.kt:29-114` performs insert-if-absent, state inspection, permit acquisition, claim, executor dispatch, and guaranteed release. Success/state-write/ACK ordering is at `module-synchronizer/src/main/kotlin/maple/synchronizer/consumer/ChunkConsumerTemplate.kt:139-158`; retryable failures remain unacked and terminal failures ACK at `module-synchronizer/src/main/kotlin/maple/synchronizer/consumer/ChunkConsumerTemplate.kt:191-243`. Decision rules are centralized at `module-synchronizer/src/main/kotlin/maple/synchronizer/state/ChunkExecutionStateMachine.kt:22-80`.
- **Verification:** The focused audit recorded `ChunkConsumerTemplateTest` (11) and `ChunkExecutionStatusTest` (13) passing. Repository tests also cover repository claims/expired leases in `module-synchronizer/src/test/kotlin/maple/synchronizer/repository/ChunkExecutionRepositoryTest.kt:47-173` (not run because it is repository/integration-oriented). Current checkout ancestry includes both the original durable state commit `f636d1a3612409c60dd5d2ad1d25dc4f8bcba70a` and PR #1463 correctness commit `ba62bf81dd27182ffe88c8c6b58a96bde03eb063`.
- **Quantitative result:** Project-level May 23–27 evidence reports 120,442 processed chunks, zero failed chunks, no Kafka lag at checkpoints, and zero restarts across 82h15m (`docs/endurance-test/endurance-report-82h.md:16-28`, `docs/endurance-test/endurance-report-82h.md:139-152`). Environment/tool conditions are the same as Candidate 2. This does not isolate the state machine's causal contribution.
- **Limitations:** Calculator idempotency is object-existence based (`module-calculator/src/main/kotlin/maple/calculator/CalculatorChunkProcessingCoordinator.kt:72-95`), not the same DB state machine. The current policy intentionally ACKs a FAILED_RETRYABLE row after its retry time is past (`module-synchronizer/src/main/kotlin/maple/synchronizer/state/ChunkExecutionStateMachine.kt:38-50`); a portfolio should explain this policy precisely instead of saying “all retryable failures always redeliver.”
- **Likely candidate contribution:** Commit metadata supports implementation/refactoring of the durable state path; endurance is a whole-pipeline outcome.

## 6. Reliability and replay: artifact preservation + deterministic result identity

**Status: VERIFIED capability; historical replay number rejected.**

- **Problem:** Recalling the external API for every calculator fix/backfill is slow, rate-limited, and may return different source data; Kafka redelivery can repeat work.
- **Cause:** Without preserved input artifacts and deterministic output identities, stages cannot be replayed independently or distinguish duplicate work.
- **Decision:** Preserve snapshot chunks under run/endpoint/chunk keys, derive deterministic result keys, republish an existing result on duplicate/replay, and retain event payload/state in `chunk_execution` for the synchronizer.
- **Implementation:** Key construction/publishing is `module-external-api/src/main/kotlin/maple/externalapi/snapshot/SnapshotSinkEventPublisher.kt:52-69`; deterministic result/republication is `module-calculator/src/main/kotlin/maple/calculator/CalculatorChunkProcessingCoordinator.kt:87-99` and `module-calculator/src/main/kotlin/maple/calculator/CalculatorChunkProcessingCoordinator.kt:132-147`; persisted event payload and identity are `module-infra/src/main/resources/db/migration/V128__chunk_execution.sql:4-31`; consumer input records the raw event payload at `module-synchronizer/src/main/kotlin/maple/synchronizer/consumer/KafkaResultChunkConsumer.kt:66-93`.
- **Verification:** `CalculatorChunkProcessingCoordinatorTest` contains duplicate/replay coverage (`module-calculator/src/test/kotlin/maple/calculator/CalculatorChunkProcessingCoordinatorTest.kt:277` onward); the focused audit recorded calculator writer and synchronizer state tests passing. PR #1463 artifact lifecycle commits `0ad44494c443e80e46f93f3d54edf190cad56fda`, `a5df4558e414f8c1a3597b21a215941425e35df4`, and `d440dcd975872896af2d45a4cfc4688a077c2ba4` are now in current checkout ancestry.
- **Quantitative result:** **Rejected:** `docs/12_Events/chunk-replay-architecture.md:38-61` reports 288,422 users, 20,257,932 items, zero errors, and 167 users/s, but supplies no date, host, heap, object-store backend, Kafka configuration, trigger command output, or raw log/counter artifact. Use it only as a lead for a reproducible replay benchmark.
- **Limitations:** Replay succeeds only while source artifacts remain; cleanup/retention is part of the correctness boundary. Result existence prevents recalculation, so a formula-versioned output key or explicit invalidation is required for intentional backfills that must overwrite semantics.
- **Likely candidate contribution:** Current artifact-key and lifecycle commits are attributable in git; replay performance is not yet portfolio-grade evidence.

## 9. Failed-design replacement: pipe streaming → temp-file drain + async multipart upload

**Status: STRONGLY VERIFIED.**

- **Problem:** Calculator produced zero-row/truncated result gzip objects; downstream synchronization received no valuation rows and the DAG could not complete.
- **Cause:** `PipedInputStream`/`PipedOutputStream` connected a producer coroutine to an AWS SDK background reader. Producer termination and SDK reads raced, causing `Read end dead` and a closed `Deflater`; a completion callback could also close the pipe mid-drain.
- **Decision:** Abandon pure pipe streaming. Fully close a bounded gzip temp file, then upload it asynchronously with `putFileAsync`; delete the temp file on completion/failure.
- **Implementation:** Current `CalculationResultWriter.kt:54-81` drains results through an `ArtifactWriter` session. `module-pipeline-artifact/.../ArtifactWriter.kt:13-45` creates the gzip temp file; `.../GzipArtifactSession.kt:42-87` closes streams before asynchronous upload and `:100-131` deletes the temp file on terminal completion. The rejected pipe design and corrective transition remain directly inspectable in commits `85b5528df557377675b080edfe7d6515c9993461` and `205ce14b814b98cf1533a8072d1393dca9cfd310`. Accepted ADR-730 captures the decision and disk trade-off at `docs/01_ADR/ADR-730_calculator-writer-temp-file-upload.md:9-66`.
- **Verification:** Corrective commit `205ce14b814b98cf1533a8072d1393dca9cfd310` (2026-06-22) follows the failed streaming commit `85b5528df557377675b080edfe7d6515c9993461` (2026-06-20). Current `CalculationResultWriterTest` passed all 3 cases in this audit, including valid JSONL decompression, empty-flow gzip, and exceptional propagation.
- **Quantitative result:** Dated 2026-06-22 E2E against MinIO, triggered through the internal ITEM_EQUIPMENT phase endpoint. Before: `calculator_chunks_processed_total=0`, a prior result part was 0 bytes, and ~14,921 `Read end dead` errors over nine minutes. After: 64 processed chunks, 0 failed, 1,948,957 calculated items, 0 `Read end dead`, and a downloaded/gunzipped result object of 674,986 bytes containing 30,507 valid JSONL rows (`docs/01_ADR/ADR-730_calculator-writer-temp-file-upload.md:70-91`).
