## 1. 배경 (Context)

### 현재 상태: In-Memory Single Flight

MapleExpectation은 현재 **SingleFlightExecutor**를 사용하여 캐시 스탬프(Cache Stampede)를 방지합니다:

```kotlin
class SingleFlightExecutor {
    // In-Memory 상태: Scale-out 불가
    private val inFlight = ConcurrentHashMap<String, CompletableFuture<*>>()

    fun <T> execute(key: String, task: () -> T): T {
        val future = inFlight.computeIfAbsent(key) {
            CompletableFuture.supplyAsync { task() }
        }
        return future.get()
    }
}
```

### 문제점: Scale-out 차단 + Hot Key 스탬프

**Scale-out Blockers 분석 결과** (docs/05_Reports/04_09_Scale_Out/scale-out-blockers-analysis.md):

| 분류 | P0 (Critical) | P1 (High) | 합계 |
|------|:---:|:---:|:---:|
| In-Memory 상태 | 6 | 6 | 12 |

**P0 Critical Blockers:**
1. **SingleFlightExecutor** - ConcurrentHashMap 사용 (인스턴스 간 공유 불가)
2. **Hot Key 스탬프** - 인기 캐릭터 100+ RPS 집중

**Hot Key 스탬프 예시:**
- **패치데이 신규 캐릭터:** 동일 장비 세팅 조회 100+ RPS
- **인기 유튜버 장비:** 동일 OCID 조회 50+ RPS
- **이벤트 아이템:** 특정 스타포스 강화 단계 집중

**In-Memory Single Flight의 문제점:**
- **멀티 인스턴스 중복 호출:** 각 인스턴스가 독립적으로 API 호출
- **캐시 스탬프 지속:** 인기 키는 여전히 동시에 로딩 시도
- **API Rate Limit 위반:** Nexon API 100 req/sec 제한 초과 위험

## 2. 결정 (Decision)

**In-Memory Single Flight을 PostgreSQL Advisory Lock + PGMQ 기반 분산 Single Flight로 대체하고, Hot Key Detection/Distribution을 추가한다.**

### 핵심 전략

#### 2.1 Distributed Single Flight (PostgreSQL + PGMQ)

**Algorithm Flow:**
```
┌─────────────────────────────────────────────────────────────┐
│ 1. Hash request key → Advisory Lock ID (FNV-1a)            │
│ 2. Try acquire advisory lock (pg_try_advisory_lock)        │
│ 3. If acquired (Leader):                                   │
│    - Execute request                                       │
│    - Broadcast result via PGMQ single_flight_results       │
│    - Release lock                                          │
│ 4. If not acquired (Follower):                             │
│    - Subscribe to PGMQ queue                               │
│    - Wait for result (timeout: 10s)                        │
│    - Return result                                         │
└─────────────────────────────────────────────────────────────┘
```

**PGMQ Message Format:**
```sql
CREATE TABLE single_flight_results (
    queue_name TEXT DEFAULT 'single_flight_results',
    msg_id BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    key VARCHAR(255) NOT NULL,
    result JSONB,
    created_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_single_flight_key ON single_flight_results(key);
```

#### 2.2 Hot Key Detection (Sliding Window Counter)

**Detection Algorithm:**
```
┌─────────────────────────────────────────────────────────────┐
│ 1. Every cache access: Increment UNLOGGED counter          │
│ 2. Sliding window: Last 10 seconds                         │
│ 3. Threshold: 100 RPS (2x average, 0.5x P99)               │
│ 4. Mark as hot key → Trigger distribution                  │
└─────────────────────────────────────────────────────────────┘
```

**UNLOGGED Table (Fast Writes):**
```sql
CREATE UNLOGGED TABLE hot_key_counters (
    key VARCHAR(255) PRIMARY KEY,
    access_count BIGINT DEFAULT 0,
    window_start TIMESTAMP DEFAULT NOW()
);

-- Periodic cleanup (every 10s)
DELETE FROM hot_key_counters WHERE window_start < NOW() - INTERVAL '10 seconds';
```

#### 2.3 Hot Key Distribution (Key Versioning)

**Distribution Strategy:**
```
Original Key: "character:12345:equipment"

Hot Key Distribution:
  - character:12345:equipment:v1 (Round-robin #1)
  - character:12345:equipment:v2 (Round-robin #2)
  - character:12345:equipment:v3 (Round-robin #3)

Access Pattern:
  Request 1 → v1 → Cache Miss → Load
  Request 2 → v2 → Cache Miss → Load
  Request 3 → v3 → Cache Miss → Load
  Request 4 → v1 → Cache Hit ✅
```

**Cooldown Strategy:**
- Hot period结束后 60 seconds cooldown
- Revert to original key
- Clear versioning metadata

## 3. 대안 (Alternatives)

### A. Redis-based Single Flight

**장점:**
- 낮은 지연 시간 (~1ms)
- Redis Pub/Sub 자체 지원

**단점:**
- Redis 인프라 의존 (P0 Blocker)
- Redis Cluster 운영 복잡도
- 비용 증가

**평가:** ❌ Scale-out 차단 요소 존재

### B. In-Memory Only (현상 유지)

**장점:**
- 최저 지연 시간 (<1ms)
- 구현 단순

**단점:**
- Scale-out 불가
- Hot Key 스탬프 지속
- 멀티 인스턴스 중복 API 호출

**평가:** ❌ P0 Blocker 미해결

### C. PostgreSQL Advisory Lock + PGMQ (선택됨)

**장점:**
- PostgreSQL 네이티브 기능 (추가 인프라 불필요)
- Scale-out 가능 (분산 락)
- Hot Key 스탬프 방지
- 단일 DB 아키텍처 부합 (ADR-001)

**단점:**
- 지연 시간 증가 (~5ms vs In-Memory <1ms)
- PGMQ 오버헤드 (~2ms)

**평가:** ✅ Scale-out 활성화 + Hot Key 해결

### D. No Single Flight

**장점:**
- 구현 불필요

**단점:**
- 캐시 스탬프 발생
- API Rate Limit 위험
- 데이터베이스 부하 증가

**평가:** ❌ 허용 불가

## 4. 기술적 구현 (Implementation)

### 4.1 PostgresSingleFlightStrategy

```kotlin
@Component
class PostgresSingleFlightStrategy(
    private val lockJdbcTemplate: JdbcTemplate,
    private val pgmqPublisher: PGMQPublisher,
    private val pgmqSubscriber: PGMQSubscriber,
    private val singleFlightMetrics: SingleFlightMetrics,
) : SingleFlightStrategy {

    override fun <T> execute(key: String, task: Callable<T>, timeout: Long): T {
        val advisoryLockId = toAdvisoryLockId(key)
        val lockKey = "single_flight:$key"

        // 1. Try acquire advisory lock
        val acquired = tryAcquireAdvisoryLock(advisoryLockId)

        return if (acquired) {
            // Leader: Execute and broadcast result
            executeAsLeader(key, task, advisoryLockId)
        } else {
            // Follower: Wait for result
            executeAsFollower(key, timeout)
        }
    }

    private fun <T> executeAsLeader(
        key: String,
        task: Callable<T>,
        advisoryLockId: Long
    ): T {
        val startTime = System.currentTimeMillis()
        try {
            val result = task.call()

            // Broadcast result via PGMQ
            pgmqPublisher.publish(
                queueName = "single_flight_results",
                message = mapOf(
                    "key" to key,
                    "result" to result,
                    "timestamp" to System.currentTimeMillis()
                )
            )

            singleFlightMetrics.recordLeaderSuccess(
                System.currentTimeMillis() - startTime,
                key
            )
            return result
        } catch (e: Exception) {
            // Publish error result
            pgmqPublisher.publish(
                queueName = "single_flight_results",
                message = mapOf(
                    "key" to key,
                    "error" to e.message,
                    "timestamp" to System.currentTimeMillis()
                )
            )
            throw ServerBaseException(ErrorCode.SINGLE_FLIGHT_EXECUTION_FAILED, e)
        } finally {
            // Release lock
            releaseAdvisoryLock(advisoryLockId)
        }
    }

    private fun <T> executeAsFollower(key: String, timeout: Long): T {
        val startTime = System.currentTimeMillis()

        // Subscribe to PGMQ queue
        val future = pgmqSubscriber.subscribe<T>(
            queueName = "single_flight_results",
            filter = mapOf("key" to key),
            timeout = timeout
        )

        try {
            val result = future.get(timeout, TimeUnit.SECONDS)
            singleFlightMetrics.recordFollowerSuccess(
                System.currentTimeMillis() - startTime,
                key
            )
            return result
        } catch (e: TimeoutException) {
            singleFlightMetrics.recordFollowerTimeout(key)
            throw ServerBaseException(ErrorCode.SINGLE_FLIGHT_TIMEOUT)
        }
    }
}
```

### 4.2 HotKeyDetector

```kotlin
@Component
class HotKeyDetector(
    private val jdbcTemplate: JdbcTemplate,
    private val hotKeyMetrics: HotKeyMetrics,
) {

    companion object {
        private const val HOT_KEY_THRESHOLD = 100 // RPS
        private const val WINDOW_SIZE_SECONDS = 10L
    }

    @Scheduled(fixedRate = 10000) // Every 10 seconds
    fun detectHotKeys() {
        val startTime = System.currentTimeMillis()

        // 1. Detect keys exceeding threshold
        val hotKeys = jdbcTemplate.queryForList(
            """
            SELECT key, access_count
            FROM hot_key_counters
            WHERE window_start > NOW() - INTERVAL '10 seconds'
              AND access_count > $HOT_KEY_THRESHOLD
            """.trimIndent()
        )

        // 2. Mark as hot key
        hotKeys.forEach { row ->
            val key = row["key"] as String
            val accessCount = row["access_count"] as Long

            hotKeyMetrics.recordHotKeyDetected(key, accessCount)
            log.info("[HotKeyDetector] Hot key detected: key=$key, rps=$accessCount")

            // Trigger distribution
            markAsHotKey(key)
        }

        // 3. Cleanup old counters
        jdbcTemplate.update(
            """
            DELETE FROM hot_key_counters
            WHERE window_start < NOW() - INTERVAL '10 seconds'
            """.trimIndent()
        )

        log.debug("[HotKeyDetector] Detection completed in {}ms", System.currentTimeMillis() - startTime)
    }

    fun recordAccess(key: String) {
        jdbcTemplate.update(
            """
            INSERT INTO hot_key_counters (key, access_count, window_start)
            VALUES (?, 1, NOW())
            ON CONFLICT (key) DO UPDATE SET
                access_count = hot_key_counters.access_count + 1,
                window_start = NOW()
            """.trimIndent(),
            key
        )
    }

    private fun markAsHotKey(key: String) {
        // Store hot key metadata
        jdbcTemplate.update(
            """
            INSERT INTO hot_keys (key, detected_at, version_count)
            VALUES (?, NOW(), 3)
            ON CONFLICT (key) DO UPDATE SET
                detected_at = NOW()
            """.trimIndent(),
            key
        )
    }
}
```

### 4.3 HotKeyDistributor

```kotlin
@Component
class HotKeyDistributor(
    private val jdbcTemplate: JdbcTemplate,
    private val hotKeyMetrics: HotKeyMetrics,
) {

    private val random = ThreadLocalRandom.current()

    fun distributeKey(key: String): String {
        // Check if key is hot
        val versionCount = jdbcTemplate.queryForObject(
            """
            SELECT version_count
            FROM hot_keys
            WHERE key = ? AND detected_at > NOW() - INTERVAL '60 seconds'
            """.trimIndent(),
            Long::class.java,
            key
        ) ?: return key // Not hot, return original

        // Distribute across versions
        val version = random.nextInt(1, versionCount.toInt() + 1)
        val distributedKey = "$key:v$version"

        hotKeyMetrics.recordKeyDistribution(key, version)

        return distributedKey
    }

    @Scheduled(fixedRate = 60000) // Every 60 seconds
    fun cooldownHotKeys() {
        val cooldownCount = jdbcTemplate.update(
            """
            DELETE FROM hot_keys
            WHERE detected_at < NOW() - INTERVAL '60 seconds'
            """.trimIndent()
        )

        if (cooldownCount > 0) {
            log.info("[HotKeyDistributor] Cooldown {} hot keys", cooldownCount)
            hotKeyMetrics.recordHotKeyCooldown(cooldownCount)
        }
    }
}
```

## 5. 트레이드오프 (Trade-offs)

### ✅ 장점 (Positive Consequences)

| 항목 | 설명 |
|------|------|
| **Scale-out 활성화** | P0 Blocker 제거, 분산 Single Flight 가능 |
| **Hot Key 스탬프 방지** | Key versioning으로 부하 분산 |
| **API Rate Limit 준수** | 중복 호출 제거 (target: >90% deduplication) |
| **단일 DB 아키텍처** | PostgreSQL만 사용, ADR-001 부합 |
| **운영 단순화** | Redis 의존 제거 |

### ⚠️ 단점 (Negative Consequences)

| 항목 | 완화 방안 |
|------|----------|
| **지연 시간 증가** | Leader: ~5ms, Follower: ~10ms (허용 가능) |
| **PGMQ 오버헤드** | 비동기 publishing, 메시지 TTL 10초 |
| **Connection Pool 사용** | 전용 풀 10 connections (ADR-003 참조) |
| **Hot Key Detection 지연** | 10초 슬라이딩 윈도우 (허용 가능) |

### Single Flight 성능

| 시나리오 | In-Memory | PostgreSQL + PGMQ | 비고 |
|----------|-----------|-------------------|------|
| Leader (실행) | <1ms | ~5ms | 허용 가능 |
| Follower (대기) | <1ms | ~10ms | 허용 가능 |
| Deduplication Rate | 0% (multi-instance) | >90% | ✅ 개선 |

### Hot Key Distribution 효과

| 시나리오 | Original | Distributed | 개선 |
|----------|----------|-------------|------|
| 100 RPS on single key | 100 RPS | 33 RPS × 3 versions | 3x 분산 |
| Cache hit rate | 0% (stomp) | 66% (2nd hit) | ✅ 개선 |
| API calls | 100 calls | 33 calls | 67% 절감 |

## 7. 리스크 및 완화 방안 (Risks)

### Risk 1: PGMQ Message Loss

**발생 조건:**
- PGMQ 큐 메시지 유실
- Follower 타임아웃

**완화 방안:**
- **Message Retention:** 10초 TTL (충분한 대기 시간)
- **Fallback:** 타임아웃 시 직접 실행 (Safe fallback)
- **Monitoring:** `single_flight_follower_timeout_total` 메트릭

### Risk 2: Hot Key Over-Distribution

**발생 조건:**
- 일시적 스파이크 트래픽을 Hot Key로 오인

**완화 방안:**
- **Threshold 조정:** 100 RPS (2x average, 0.5x P99)
- **Sliding Window:** 10초 평균 (일시적 스파이크 필터링)
- **Cooldown:** 60초 후 자동 해제

### Risk 3: Advisory Lock Contention

**발생 조건:**
- 동일 키에 다수 인스턴스 경합

**완화 방안:**
- **Leader-Follower Pattern:** 오직 1개 Leader만 실행
- **Fast Follower:** PGMQ 결과 대기 (Lock 대기 아님)
- **Connection Pool:** 전용 풀 10 connections (ADR-003 참조)

### Prometheus 메트릭

```yaml
groups:
  - name: single_flight_alerts
    rules:
      - alert: SingleFlightDeduplicationLow
        expr: rate(single_flight_deduplication_total[5m]) / rate(single_flight_requests_total[5m]) < 0.9
        for: 5m
        annotations:
          summary: "Single flight deduplication rate < 90%"

      - alert: HotKeyDetectionLatencyHigh
        expr: histogram_quantile(0.99, hot_key_detection_duration_seconds) > 0.001
        for: 5m
        annotations:
          summary: "Hot key detection latency p99 > 1ms"

      - alert: SingleFlightFollowerTimeoutHigh
        expr: rate(single_flight_follower_timeout_total[5m]) / rate(single_flight_requests_total[5m]) > 0.01
        for: 5m
        annotations:
          summary: "Single flight follower timeout rate > 1%"
```

### 모니터링 쿼리

```sql
-- Active hot keys
SELECT
    key,
    version_count,
    detected_at,
    NOW() - detected_at as age
FROM hot_keys
WHERE detected_at > NOW() - INTERVAL '60 seconds'
ORDER BY detected_at DESC;

-- Hot key access statistics
SELECT
    key,
    access_count,
    access_count / 10 as rps -- 10 second window
FROM hot_key_counters
WHERE access_count > 100
ORDER BY access_count DESC;

-- Single flight results queue depth
SELECT
    count(*) as queue_depth,
    min(created_at) as oldest_message,
    max(created_at) as newest_message
FROM single_flight_results;
```
